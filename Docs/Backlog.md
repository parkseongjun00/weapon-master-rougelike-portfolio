# 재검토 후보 백로그

> 공개 편집본 p1 · 2026-10-23 · 원본 `703affa`. 현재 안내는 [공개본 문서 색인](README.md)을 따른다. 과거 기록은 당시 상태이며 현재 코드 전체의 검증 결과가 아니다.

- 버전: v0.12
- 수정일: 2026-10-19

이 문서는 **미루기 위한 공간**이다. '지금 당장 할 일은 아니지만 언젠가는 해야 할 일'을 모아두고, 나중에 그 일을 실제로 집어들 때 처음부터 다시 조사하지 않아도 되도록 맥락(왜 필요한지, 왜 지금은 아닌지, 무엇이 재검토 트리거인지)을 미리 저장해두는 살아있는 목록이다.

`DevNotes/`는 확정된 결정과 이유를 기록하는 append-only 히스토리다. 이 문서는 보류 과제의 검토 맥락을 관리하고, 착수·완료·폐기 뒤에는 번호·제목·처리 결과와 보존 기록 위치만 남긴다.

**작성 규칙**
- 항목은 일의 단위로 나누고, 각 항목을 **배경**(어떤 맥락에서 필요성을 느꼈는지) / **전략**(어떻게 해결할지, 검토한 대안 포함) / **기대효과**(선택, 없으면 생략) 3단으로 구성한다.
- 경위 전체를 다시 옮겨 적지 않는다. 필요하면 `DevNotes/`의 해당 기록 파일과 섹션을 포인터로 가리킨다.
- 제목 끝에 `[보류]`·`[착수]`·`[완료]`·`[폐기]`로 상태를 표시한다. `[착수]`는 실행 범위가 확정되어 작업을 시작한 상태이며 완료를 뜻하지 않는다.
- 착수·완료 시 확정된 결정과 구현 결과는 `DevNotes/`의 관련 기록 파일에 보존하고, 이 문서에는 번호·제목과 상태, 처리일·결과·보존 기록 위치를 짧게 남긴다.
- 폐기 시 판단과 사유를 관련 `DevNotes/`에 보존하고, 이 문서에도 번호·제목과 `[폐기]`, 처리일·짧은 사유·보존 기록 위치를 남긴다.
- 긴 본문은 보존할 내용의 이관을 확인한 뒤 정리한다. 실행 중 계획은 해당 작업 세션에서 관리하며, 다른 세션에 필요한 진행·검증 상태는 HANDOFF에 요약한다.
- 항목 번호는 고정 식별자이며 우선순위가 아니다. 재번호·재사용하지 않고 새 항목에는 기존 최대 항목 번호 다음 값을 부여한다. 변경 이력의 장 번호는 항목 번호에 포함하지 않는다.
- 항목 앞의 고정 앵커는 제목·상태가 바뀌어도 유지한다. 다른 문서에서는 상태에 따라 달라지는 제목 앵커 대신 이 앵커로 연결한다.
- 신규 후보가 생기면 여기 바로 추가한다. `DevNotes/`의 결정 섹션 안에 흩어 놓지 않는다.

<a id="1-stage1scenebuildercs-관심사-분리"></a>

## 1. `Stage1SceneBuilder.cs` 관심사 분리 [보류]

**배경**: 1300줄이 넘고 서로 무관한 관심사(아레나/무기/적/증강/캐릭터/UI/칭호)가 한 파일에 몰려 있어 코드 리뷰에서 제외된 상태다(2026-08-21 논의).

**전략**: 관심사별 static 클래스(`ArenaBuilder`/`WeaponBuilder`/`CharacterBuilder` 등)로 분리하고, `Stage1SceneBuilder.BuildScene()`은 각 도메인 빌더를 순서대로 호출하는 얇은 오케스트레이터로 남긴다. 다른 컴포넌트가 이 클래스를 참조하지 않아(코드 상 언급 전무, 한국어 주석 교차 참조만 존재) 리팩토링 리스크 자체는 낮은 편.

**기대효과**: 코드 리뷰 재개 가능. 관심사별 탐색이 쉬워짐.

## 2. `WeaponDefinition.hasCondition`/`startsDiscovered` 필드 구조 정리 [보류]

**배경**: 둘 다 사실상 '맨손만을 위한 예외 필드'라는 지적이 있었다(→ `DevNotes/02-MetaSystems.md` §2.13).

**전략**: 두 필드를 한꺼번에 정리할 더 나은 구조가 떠오르면(예: '맨손을 다른 무기와 다르게 취급하는 개념' 자체를 명시적인 하나의 축으로 묶는 방식) 그때 리팩토링한다. 무기 종류가 늘어나 이 모양이 계속 어색해지면(예: '발견 없이 시작하는 무기'가 여러 개로 늘어나면) 우선순위를 올린다.

## 3. `WeaponSpawner` 오브젝트 풀링 [보류]

**배경**: 2단계에서 '3단계 무기 등급/희귀도 리팩터 때 같이 처리'하기로 보류됐다(→ `DevNotes/01-LoopSupport.md` §1.7). 그 리팩터는 이미 끝났는데 실제로 처리됐는지는 현재 코드/`DevNotes/` 어디에도 완료 기록이 없어 불명확하다.

**전략**: 먼저 실제로 처리됐는지 코드로 재확인한다. 안 됐다면 `EnemySpawner`와 동일한 체크아웃/반납 패턴을 적용한다.

**기대효과**: 반복 스폰 시 GC 압박 감소. 다만 무기 필드 스폰은 고정 스폰 포인트에서 저빈도로만 일어나 원래도 우선순위가 낮았던 항목이라, 실익은 크지 않을 수 있다.

## 4. `PlayerAugmentManager._augmentInstancesByStat` 타이밍 주석 정리 [보류]

**배경**: 증강 배율 개편(→ `DevNotes/02-MetaSystems.md` §2.16) 이후 더는 필요 없어진 'Awake 아니라 필드 초기화 시점' 관련 주석이 그대로 남아있다.

**전략**: 배열을 다시 `Awake()` 안에서 만들도록 되돌리고 주석을 정리한다. 정확성엔 영향 없는 사소한 후속 정리라 급하지 않다.

<a id="5-신규-무기-서브타입-도입-여부"></a>

## 5. 신규 무기 서브타입 도입 여부 [보류]

**배경**: GDD 5.1의 중량형 근접/강격형 원거리 등. 3단계 메타 진행 재설계 중 메타 해금과의 연결고리가 사라지며 범위에서 빠졌다(→ `DevNotes/02-MetaSystems.md` §2.15).

**전략**: 5단계(콘텐츠 확장) 착수 시 도입 여부를 확정하고, 도입한다면 무기 도감 슬롯이 늘어나는 것과 어떻게 연결할지(아래 '무기 도감 슬롯에 등급 축 추가' 항목과 연계) 함께 정한다.

**기대효과**: 무기 다양성 확대.

---

<a id="6-난이도-스스로-올리기-dead-cells-boss-cell식"></a>

## 6. 난이도 스스로 올리기 (Dead Cells Boss Cell식) [보류]

**배경**: 메타 진행은 파워에 절대 관여하지 않는다는 원칙(GDD) 때문에, '성장감이 없어 장기 동기가 떨어지지 않는가'라는 우려가 3단계 재설계 논의 중 나왔다(→ `DevNotes/02-MetaSystems.md` §2.15).

**전략**: 3단계 결과물(등급/칭호/도감)을 플레이테스트해보고 성장감 부족이 실제로 체감되면, 캐릭터가 아니라 도전 난이도가 스스로 성장하는 권리를 해금하는 방식을 검토한다.

**기대효과**: 파워 인플레이션 없이 장기 동기 부여.

---

<a id="7-무기-도감-슬롯에-등급rarity-축-추가-여부"></a>

## 7. 무기 도감 슬롯에 등급(Rarity) 축 추가 여부 [보류]

**배경**: 원래 '무기 종류 × 등급' 8칸 설계였으나, 등급이 무기 종류에 고정된 값으로 바로잡히며 이 전제가 깨져 '무기 정의 단위' 슬롯으로 축소 확정됐다(→ `DevNotes/02-MetaSystems.md` §2.13).

**전략**: 신규 무기/서브타입 추가로(위 '신규 무기 서브타입 도입' 항목 참고) 등급별 로스터가 실제로 늘어난 뒤 재검토한다.

**기대효과**: 도감 콘텐츠 볼륨 확대.

<a id="8-stage1scenebuilderbuildplayeranimatorcontroller-stale-상태-정리"></a>

## 8. `Stage1SceneBuilder.BuildPlayerAnimatorController` stale 상태 정리 [보류]

**배경**: 컨트롤러 파일이 이미 있으면 그냥 반환하고 끝나는 가드 때문에 실제로 재실행되는 일이 없다 보니, `§3.4`(Meshy 파일명 정리, `DevNotes/03-PlayerAnimation.md` §3.4)의 fbx 파일명 변경과 `§3.6`(Upper Body 레이어 신설, `DevNotes/03-PlayerAnimation.md` §3.6)이 이 함수에 전혀 반영되지 않은 채로 코드에 남아있다. 이 함수를 지금 실제로 실행하면(예: 컨트롤러 파일을 지우고 재생성) 옛 파일명 참조 때문에 바로 깨진다.

**전략**: 다음에 이 함수를 실제로 만질 일이 생기면(예: 신규 캐릭터 추가로 컨트롤러를 다시 생성해야 하는 상황) fbx 경로를 현재 파일명으로 맞추고, `PlayerUpperBodyLayerSetup.Setup()` 호출을 이 함수 끝에 합쳐서 "컨트롤러 최초 생성"과 "레이어 구성"이 다시 하나의 소스로 합쳐지게 한다. 지금 당장은 이 함수가 실행될 일이 없어(가드 때문에) 급하지 않다.

<a id="9-조준-방향과-이동-방향이-다른-경우의-로코모션"></a>

## 9. 조준 방향과 이동 방향이 다른 경우의 로코모션 [보류]

**배경**: 사용자가 조준 방향을 유지한 채 반대 방향으로 이동하면 실제 이동은 뒤쪽인데, 현재 Animator는 이동 속도만 받아 전진 로코모션을 재생한다. 시각적 이동 방향과 실제 위치 변화가 다르다.

**전략**: (Codex 제안) 조준 방향을 유지하는 현재 조작 명세(GDD 6.3)를 보존하고, 이동 벡터를 캐릭터 로컬 좌표로 변환해 전후·좌우 방향을 Animator에 전달하는 2D 로코모션 블렌드 트리를 검토한다. 전진·후진·좌우 이동용 루프 애니메이션을 확보한 뒤, 현재 Humanoid 리그에서 방향별 클립의 발 위치와 속도가 실제 이동 속도에 맞는지 확인한다.

**기대효과**: 조준과 이동을 독립적으로 조작할 때도 화면상의 보행 방향이 실제 이동 방향과 일치.

<a id="10-weaponbase-하위-클래스-inspector-구조-정리"></a>

## 10. `WeaponBase` 하위 클래스 Inspector 구조 정리 [보류]

**배경**: 현재 `WeaponGripPointEditor` 하나가 `WeaponBase` 공통 데이터, 실제 하위 타입별 데이터, 저작 경고와 버튼을 함께 그린다. 하위 클래스와 저작 기능이 늘어나면 타입별 표시 조건과 Inspector 책임을 추적하기 어려워질 수 있다.

**전략**: `WeaponBase` 공통 표시와 `MeleeWeapon`·`RangedWeapon` 전용 표시의 책임을 먼저 정리한다. 실제 중복과 변경 빈도를 확인한 뒤 공통 그리기 도우미, 타입별 Custom Editor, Property Drawer 중 가장 작은 구조를 선택한다.

**기대효과**: 하위 클래스별 필드 누락과 잘못된 표시 조건을 줄이고 Inspector 변경 범위를 명확히 한다.

<a id="11-editor-코드의-문자열-기반-직렬화-필드-탐색-검토"></a>

## 11. Editor 코드의 문자열 기반 직렬화 필드 탐색 검토 [보류]

**배경**: `SerializedObject.FindProperty`와 `SerializedProperty.FindPropertyRelative`가 문자열로 필드 경로를 찾는다. 런타임 필드명이 바뀌어도 Editor 코드가 컴파일되므로 Inspector가 실행될 때 누락이나 오류가 발생할 수 있다.

**전략**: Editor 코드의 문자열 필드 경로를 전수 확인한다. `nameof`를 적용할 수 있는 경로는 교체하고, Unity API 제약으로 문자열이 필요한 경로는 상수 집중, 명시적 누락 검사, Editor 검증 테스트 중 필요한 보호 수단을 적용한다.

**기대효과**: 직렬화 필드 이름 변경이 Inspector의 지연 오류로 이어지는 위험을 줄인다.

<a id="12-무기-editor-도구의-역할책임-재정리"></a>

## 12. 무기 Editor 도구의 역할·책임 재정리 [보류]

**배경**: `Assets/Scripts/Editor/Weapons`에는 무기 프리팹 생성, Inspector 저작, 전용 씬 관리가 함께 있으며 기능 추가를 우선해 파일 내부 책임과 최소 단위 구분을 충분히 검토하지 않았다. Editor 코드도 변경이 누적되면 탐색과 회귀 확인 비용이 커지므로 역할 경계를 별도로 점검할 필요가 있다.

**전략**: 항목 10의 하위 클래스 Inspector 구조와 항목 11의 문자열 기반 직렬화 필드 탐색을 함께 조사한다. 실제 중복과 변경 축을 기준으로 프리팹 생성, Inspector 표시·검증, 저작 씬 조작, GripPoint 계산 책임을 최소 단위로 나누되, 현재 파일 구성이 충분한 부분에는 새 추상화를 추가하지 않는다. `Stage1SceneBuilder`와 중복된 무기 생성 책임이 확인되면 항목 1의 관심사 분리와 연결해 단일 저작 경로를 정한다.

**기대효과**: Editor 전용 코드도 역할과 변경 범위가 명확해지고, 무기 저작 기능을 추가할 때 한 파일에 책임이 다시 집중되는 것을 줄인다.

<a id="13-무한형-맵-구조-검토-및-프로토타입"></a>

## 13. 무한형 맵 구조 검토 및 프로토타입 [보류]

**배경**: 엔드리스 런과 맵의 공간 구조를 분리하고, 맵마다 제한형 또는 무한형을 선택할 수 있도록 확장했다. 첫 번째 맵은 핵심 전투와 공간 밀도 검증을 위해 제한형으로 유지하며, 무한형 맵은 포스트-MVP 콘텐츠로 보류한다(GDD 3장).

**전략**: (Codex 제안) 첫 번째 제한형 맵에서 코어 전투를 검증한 뒤, 플레이어 주변 공간 조각의 생성·재활용, 적과 필드 무기의 스폰·제거 범위, 길과 건물 연결 규칙, 장시간 이동 시 좌표 정밀도와 내비게이션 처리를 작은 프로토타입으로 검토한다. 기존 `ArenaBounds`에 무한형 동작을 억지로 추가하지 않고, 공통 규칙과 맵 유형별 책임의 실제 차이를 확인한 뒤 가장 작은 구조를 선택한다.

**기대효과**: 제한형 맵의 단순성을 유지하면서 맵별 이동·탐색 감각을 확장할 수 있는지 낮은 비용으로 판단.

## 14. 고정 시점 카메라의 건물 내부 진입 방지 [보류]

**기준**: [첫 맵 기준 6장](Art/FirstMap.md#6-카메라-정책과-후속-과제). 환경 리소스 제작과 분리해 다룬다.

**배경**: 사용자 승인으로 Cinemachine 3.1.7·Follow·Deoccluder와 상체 기준점·기존 휠 줌 연결을 적용했다. 컴파일과 직접 API68개·Play12개 검증을 완료했다. 현재 구현·설정·검증 범위는 [개발 노트3.27](DevNotes/03-PlayerAnimation.md#327-deoccluder로-낮은-건물의-시야-가림-대응)에 보존한다. 이 항목은 남은 직접 플레이·외관·빌드 확인을 위한 기록이다.

**전략**:

- 벽 밀착 시 확대 정도와 주변 적·드롭 무기의 가독성, 이동·충돌 전환 중 마우스 조준·공격 감각을 사용자 직접 플레이로 확인한다.
- 건물24개 위치(북쪽22·남쪽2)의 충돌·상체 시선 검사와 전체 모서리·차양·돌출 외관의 화면 합격을 구분한다. 기존 Collider 밖의 메시에서 잔여 침범이 확인되면 해당 범위를 조사한다.
- FOV30·45·60과 4:3·16:9·21:9의 안전 반경 포함 계산은 완료했다. 실제 화면과 다른 극단적 화면 비율은 별도 확인한다.
- 장시간 전투·실행 빌드와 물리 검사 비용을 확인한다. Editor 검사를 빌드 성능 수용으로 대체하지 않는다.
- 최소 거리·상승·측면 우회·추가 충돌체는 관찰된 한계가 있을 때 별도 범위로 검토한다. 상체 기준점 시야 확보와 선택 투명화 항목15를 구분한다.
- 착수 트리거: 사용자 직접 플레이 또는 후속 외관·빌드 검증 요청. 현재 기록은 추가 우회·투명화 구현 승인이 아니다.

**기대효과**: 적용된 충돌 대응과 실제 조작·화면·성능 수용을 구분해 완료를 판단한다.

<a id="15-건물-시야-가림-허용-및-불투명도-조절-검토"></a>

## 15. 건물 시야 가림 허용 및 불투명도 조절 검토 [보류]

**기준**: [첫 맵 기준 6장](Art/FirstMap.md#6-카메라-정책과-후속-과제). 자동 근접의 맥락 전달·접근 감쇠·건물 페이드는 사용자 결정(2026-10-17)으로 보류한다.

**배경**: 기존의 단순 가림 허용에서 사용자 승인(2026-10-16) Deoccluder 적용으로 상체 기준점 시야 확보를 시도하는 동작으로 전환했다. 현재 정책은 FirstMap 6장, 구현은 개발 노트3.27을 따른다. 주변 전투 공간까지 부족할 때의 불투명도(Opacity) 조절은 선택 사항이며 적용 여부와 수치는 미확정이다.

**전략**:

- 사용자 보류 결정(2026-10-17): 다른 작업을 우선하며 접근·복귀 감쇠 조정과 건물 페이드 조합은 지금 적용하지 않는다.
- 사용자 배경 의견: 자유로운 카메라 위치·회전 조작이 없어 장애물과 자동 근접의 관계를 플레이어가 스스로 확인하기 어려울 수 있다. 실제 혼란의 관찰 결과나 자유 카메라 구현 요청으로 해석하지 않는다.
- 재검토 후보: 가리는 건물의 알파 반투명화·디더 페이드·부분 마스킹과 완만한 접근을 조합한다.
- 기술 경계: 페이드는 렌더링, 접근 감쇠는 카메라 이동, Collider는 물리 충돌을 담당한다. 페이드가 벽 관통 방지를 자동으로 해결하지 않는다.
- 우선 비교 후보(Codex 제안): 대표 건물 한 채에서 디더 페이드와 접근 감쇠를 비교한다. 건물 단위 Renderer·재질·그림자 복원과 실행 빌드 비용을 확인한다.
- 근거: [Unity Shader Graph Dither](https://docs.unity3d.com/Packages/com.unity.shadergraph@17.0/manual/Dither-Node.html), [Unity Deoccluder](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/CinemachineDeoccluder.html).
- 젤다 야숨·왕눈의 건물 페이드 기억은 사용자 경험이며 공식 구현 확인 사실로 기록하지 않는다.

- 현재 Deoccluder의 확대 정도와 가림 해소 후의 전투 공간을 확인한 뒤 보조 표현의 필요성을 판단한다.
- 사용자 검토 요청: 보조 표현을 도입한다면 가리는 건물의 불투명도를 조절하는 수준을 먼저 검토한다.
- (Codex 제안) 적용 시 몸체·창문·간판·옥상 구조물의 표시를 건물 단위로 맞추고, 충돌은 유지한다. 투명해진 곳을 통행 가능한 길로 오해하지 않는지 검증한다.
- URP 재질의 투명 렌더링 설정, 겹침과 깊이 정렬, 그림자, 표시 전환의 깜빡임과 성능을 확인한다. 참고: [Unity URP Lit Shader 공식 문서](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/lit-shader.html).
- 착수 트리거: 현재 시야 보정의 플레이테스트 이후 사용자가 보조 표현 검토를 승인한 시점이다. 자동 근접의 안내·연출과 투명화는 이번 구현에 포함하지 않았다.

## 16. NW03 현실성 개선과 환경 리소스 검증 [보류]

**기준**: [첫 맵 제작 방향](Art/FirstMap.md#71-사용자-확인-제작-방향), [NW03 구현 기록](DevNotes/04-EnvironmentArt.md). 2026-10-13에 이전 논의 초안의 미확정 개선안을 이 항목으로 이관했다.

**배경**: NW03 한 채의 단순 기하와 독립 재질 기반은 구현되었으나, 사용자 피드백에서 출입구·창문 깊이와 점포 차이가 부족하고 전체 화면의 비주얼이 단순하게 보였다. 임시 카메라 렌더는 확보했지만 유효한 Play Mode 외관 검증과 실행 빌드 성능 측정은 완료하지 않았다.

**전략**:

- (Codex 제안) 한 점포의 출입문·쇼윈도·간판·차양을 먼저 다듬고 같은 시점의 전후 화면으로 효과를 평가한다.
- (Codex 제안) 두 점포의 외관 차이, 접합부·마감, 재질 크기·광택, 필요한 설비를 단계별로 검토한다.
- 간판 앞면 이미지 교체 흐름은 사용자 확인 방향이며, 실제 상호·글자·그래픽 제작과 적용은 미착수 상태다.
- (Codex 제안) 소재 확인용 중립 조명 미리보기와 현재 게임 조명을 비교한다. 게임 씬 조명 변경은 별도 요청으로 판단한다.
- 실제 Play Mode에서 NW03 외관을 확인하고, 실행 빌드에서 목표 기기·동시 표시 건물 수·재질·텍스처·그림자를 포함한 프레임 시간과 메모리를 측정한다.
- 최종 폴리곤·재질·텍스처 예산, 재사용 부품의 범위와 다른 건물 반복 제작의 합격 기준을 정한다.
- 착수 트리거: 사용자가 구체적인 다음 실행 범위를 승인한 시점이다. 이번 기록은 분식집 전면 개선이나 전체 맵 확대 제작 승인이 아니다.
- 카메라 내부 진입 방지와 불투명도 검토는 항목 14·15에서 독립적으로 다룬다.
- 이전 초안의 작업 경계: NW03 위치·20×26m 외곽·2층 몸체·점포 구획, 기존 충돌·통행·카메라·단색 유리를 유지하고 기존 시제품을 보관하며 비교한다.
- (Codex 제안) 분식집 전면 → 국수집과 점포 차이 → 벽돌·금속·도장·천·콘크리트 재질 → 간판 고정 부분·옥상 설비·필요한 벽등과 사용 흔적 → 런타임·성능·재사용 검증 순서로 검토한다.
- (Codex 제안) 전면은 출입문·쇼윈도·창틀·문턱·손잡이·간판·차양의 연결과 깊이를 우선한다. 문 폭 1.0~1.2m·높이 2.1~2.3m, 벽 분할로 개구부 깊이 표현, 작은 모따기는 시험 후보이며 확정 치수가 아니다.
- (Codex 제안) 가상 분식·국수 간판과 점포별 입구·차양·프레임 조합을 비교한다. 반사·내부 투시를 추가하는 방향은 기존 단색 유리 기준과 구분한다.
- 평가 기준: 같은 구도의 전후 화면에서 확대 없이 문·쇼윈도·간판과 점포 차이가 보이는지, 창문·간판·차양이 벽에 설치된 형태로 읽히는지 확인한다. 재질 수나 폴리곤 수 자체를 합격 기준으로 삼지 않는다.

**기대효과**: 대표 건물에서 외관 완성도와 제작·성능 기준을 확보한 뒤 다른 상가로 재사용할 수 있다.

## 17. 캐주얼 생존 난투 PVP와 추가 스테이지 [보류]

**배경**: 사용자는 주변 물건 확보·교체 중심의 즉흥 난투를 장기적으로 캐주얼한 배틀로얄 느낌의 PVP로 확장하고 싶다고 밝혔다. 장소도 한국 상가 거리 하나로 한정하지 않고 여러 스테이지로 확장하는 방향을 확인했다.

**전략**:

- 먼저 현재 싱글플레이에서 물건 확보·교체·이동 판단의 재미를 검증한다.
- PVP는 장기 구상으로 유지한다. 인원·승리 조건·맵 크기·빌드·네트워크 방식은 미확정이며 현재 구현 범위에 포함하지 않는다.
- 착수 검토 시 동시 픽업, 공격 판정과 상태 동기화의 비용을 확인한다. 현재 코드에 네트워크 구조를 선행 도입하지 않는다.
- 추가 스테이지는 장소·수량·제작 시점이 미확정이다. 첫 맵을 검증한 뒤 장소별 물건과 전투 공간이 다른 판단을 만드는지 검토한다.
- 착수 트리거: 사용자가 PVP 조사 또는 다음 스테이지의 구체적인 기획 범위를 요청한 시점이다.

## 18. 적의 물건 확보와 원거리 공격 확장 [보류]

**배경**: 적 콘셉트 탐색 중 원거리 적 후보로 물건을 던지는 적과 새총·폭죽·개조 발사기가 제안되었다. 적도 현장의 물건을 확보하면 플레이어와 물건을 둘러싼 경쟁이 생길 수 있으나 신규 행동이 필요하다.

**전략**:

- 외형·성격 후보는 [적 디자인 기준](Art/EnemyDesign.md#6-후속-후보와-열린-질문)과 현재 논의 초안에서 검토한다.
- 원거리 적 채택 시 공격 거리·투사체·준비 동작·주기·거리 유지 여부를 GDD에서 확정한다.
- 미확정 기능 후보: 적이 바닥 물건을 찾아 집고 사용하는 행동, 동시 픽업 처리, 플레이어의 장착 물건 투척, 배경 물체의 집기·파괴 확대.
- 고정된 투척 물건을 사용하는 표현과 실제 필드 물건 확보 AI를 구분한다.
- 착수 트리거: 대표 적 디자인 검토 후 사용자가 해당 공격 유형이나 물건 상호작용의 기획·구현 범위를 요청한 시점이다.

## 19. 다중 링 실제 플레이와 성능 수용 [보류]

**배경**: 다중 링 구현·자동 검증은 완료했으나 직접 플레이와 최종 실행 환경의 수용 확인이 남아 있다. 64명 이동 갱신 CPU 표본이 3.61ms에서 5.52ms로 증가했다. 측정 조건·한계와 근거는 [개발 노트 5.11](DevNotes/05-EnemyAnimation.md#511-몸체-기반-다중-링-슬롯)을 따른다.

**전략**:

- 직접 조작에서 F8 20명·반복 생성으로 추적·안쪽 충원·밀집·이동 중 겹침을 확인한다.
- 유형별 공격 적용 후 혼합 크기 유닛의 도착 거리와 공격 범위·회피 가능성을 확인한다(GDD 6.1).
- 장시간 군집과 전체 런 사망·재시작 후 예약·풀·보상 상태를 확인한다.
- 목표 기기·동시 적 수를 명시해 전체 프레임 CPU·GC와 실행 빌드 성능을 측정한다. 허용 비용을 정한 뒤 최적화 필요성과 범위를 판단한다.
- 슬롯 배정과 장애물 우회 경로 탐색을 구분한다. 도달성 문제가 관찰되면 경로 탐색 도입을 별도 검토한다.
- 착수 트리거: 사용자 직접 테스트 또는 성능·최종 빌드 검증 요청. 이번 문서 정리는 추가 최적화·경로 탐색 구현을 포함하지 않는다.

**기대효과**: 자동 검증 결과와 실제 플레이·성능 수용을 구분해 최종 완료를 판단한다.

## 20. 적 간 공격 유도와 상황 반응 말풍선 [보류]

**배경**: 사용자는 자유로운 전투의 폴리싱 후보로 적의 공격에 다른 적이 맞는 상황과 이에 반응하는 머리 위 말풍선을 제안했다. 플레이어가 적의 공격을 유도하여 적끼리 충돌하는 상황을 만들고, 그 결과를 대사로 전달하는 방향을 검토한다.

**전략**:

- 유형별 공격의 기본 대응을 확인한 뒤 전투 폴리싱에서 재검토한다.
- 공격 상호작용 후보: 플레이어가 피하거나 위치를 바꿔 적의 공격에 다른 적이 맞도록 유도한다.
- 말풍선 후보: 간헐적인 도발과 공격 결과에 대한 반응을 표시한다.
	- 도발 예시: "가만 두지 않겠다!", "이 녀석 덤벼라!"
	- 반응 예시: "아잇! 아프잖아!", "어떤 자식이 아군을 때리냐?!"
- 실제 적 간 피해·경직을 허용할지, 피격 표현만 사용할지는 미확정이다.
- 대상 공격·피해량·발동 조건·말풍선 빈도·동시 표시 수·공격 예고와의 가독성은 착수 시 정한다.
- 착수 트리거: 기본 공격 패턴의 플레이 확인 후 사용자가 전투 상호작용·말풍선 폴리싱 검토를 요청한 시점이다.
- 현재는 아이디어 보존이며 GDD의 피해 대상 규칙 변경이나 기능 구현을 뜻하지 않는다.

**기대효과**: 위치 선정과 공격 유도로 적 사이의 상호작용을 만들고, 상황별 대사로 그 결과와 적의 성격을 전달한다.
