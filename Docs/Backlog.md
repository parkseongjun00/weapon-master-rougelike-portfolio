## 0. 일러두기

- **목적과 등록**
	- 사용자가 다시 다룰 일로 정한 기획·기술 과제를 보존한다.
	- 신규 등록·재등록·범위 확대는 사용자 요청이나 등록안에 대한 동의가 필요하다.
	- AI가 아이디어·개발 계획·남은 검증을 임의로 등록하지 않는다.
- **작성**
	- 과제는 문제·전략으로 작성하고, 중요한 선행 조건·보류 사유는 내용에 포함한다.
	- 확정 사항·사용자 의견·AI 제안을 구분한다.
	- 비교는 표, 독립적인 요점은 불릿, 연결된 설명은 짧은 문단으로 쓴다.
- **번호와 참조**
	- 보류 과제는 1장의 H3로 나누고 순서대로 번호를 매긴다. 상태는 [보류]·[착수]로 표시한다.
	- 참조에는 번호·상태와 무관한 고정 앵커와 과제명을 사용한다.
- **처리와 보존**
	- 완료·철회 결과는 별도 H2의 처리 표에 짧게 남기고, 장기적인 결정·구현 결과는 DevNotes에 보존한다. 빈 처리 장은 만들지 않는다.
	- 등록 취소·완전 삭제 요청은 항목·앵커·관련 참조까지 정리하며 임의로 복원하지 않는다. 과거 본문은 Git 이력으로 확인한다.
	- 문서 변경 이력은 마지막 H2에 기록한다.

## 1. 보류 과제

### 1.1 씬 빌더의 제작 책임 분리 [보류]

<a id="scene-builder-responsibilities"></a>

- **문제**
	- 아레나·무기·적·캐릭터·UI 제작이 Stage1SceneBuilder 한 파일에 모여 탐색과 검토가 어렵다는 기존 기록이 있다.
	- 당시 줄 수와 참조 범위는 현행 코드 확인이 필요하다.

- **전략**
	- 실제 책임과 중복을 확인해 아레나·무기·캐릭터·UI의 제작 경계를 나눈다.
	- BuildScene은 제작 순서와 연결만 담당하도록 검토한다.

### 1.2 맨손 전용 무기 속성 정리 [보류]

<a id="unarmed-weapon-properties"></a>

- **문제**
	- 기존에는 hasCondition·startsDiscovered가 사실상 맨손만의 예외를 나타냈다.
	- 이후 무기 데이터 구조가 바뀌었으므로 현재도 같은 문제가 남는지 확인이 필요하다.

- **전략**
	- [당시 도감 결정](DevNotes/02-MetaSystems.md#213-무기-도감-최소-구조)과 [프리팹 내장 데이터 전환](DevNotes/03-PlayerAnimation.md#317-프리팹-중심-무기-데이터와-스폰-등록-통합)을 기준으로 현행 필드·사용처를 확인한다.
	- 맨손 예외가 여전히 여러 플래그에 흩어져 있다면 함께 정리할 최소 구조를 검토한다.

### 1.3 필드 무기 스폰의 풀링 필요성 검토 [보류]

<a id="weapon-spawn-pooling"></a>

- **문제**
	- WeaponSpawner의 풀링은 저빈도 생성을 이유로 보류됐으며 적용 여부는 확인이 필요하다.
	- 생성 빈도가 낮아 풀링의 실익도 작을 수 있다.

- **전략**
	- 현재 생성·제거 경로와 빈도를 확인한다.
	- 풀링이 필요하면 기존 풀의 체크아웃·반납 방식을 재사용하되, 실제 무기 재사용 초기화 범위도 확인한다.
	- 당시 판단은 [개발 노트 1.7](DevNotes/01-LoopSupport.md#17-오브젝트-풀링-도입-범위)을 따른다.

### 1.4 조준·이동 방향별 로코모션 [보류]

<a id="directional-locomotion"></a>

- **문제**
	- 조준 방향을 유지한 채 뒤·옆으로 움직여도 전진 모션을 재생한다는 문제가 기록돼 있다.
	- 방향별 모션은 과거 기각 기록도 있으므로 기존 판단과 이번 요구를 구분해야 한다.

- **전략**
	- 조준·이동의 독립 조작을 유지한다.
	- Codex 제안: 로컬 이동 벡터와 전후·좌우 클립을 사용하는 2D 블렌드 트리를 비교한다.
	- 클립 확보 비용, 발 위치·재생 속도와 실제 이동의 일치를 확인한다.
	- 기존 기각 사유는 [개발 노트 3.5](DevNotes/03-PlayerAnimation.md#35-이동-방향과-조준애니메이션-방향-불일치-2d-blend-tree-검토-후-기각)를 참고한다.

### 1.5 무기 타입별 Inspector 표시 분리 [보류]

<a id="weapon-inspector-layout"></a>

- **문제**

	- 기능 증가로 타입별 필드 누락이나 표시 조건 추적이 어려워질 수 있다.

	- 공통 그리기 도우미·타입별 Custom Editor·Property Drawer 중 필요한 최소 구조를 선택한다.

### 1.6 Editor 직렬화 필드 경로의 변경 안전성 [보류]

<a id="serialized-property-paths"></a>

- **문제**
	- FindProperty·FindPropertyRelative의 문자열 경로는 필드 이름을 바꿔도 컴파일을 통과할 수 있다.
	- Inspector 실행 시점에 누락·오류가 드러나는 위험이 있다.

- **전략**
	- Editor의 문자열 필드 경로를 확인하고 nameof를 사용할 수 있는 위치는 교체를 검토한다.
	- 문자열이 필요한 경로는 상수 집중·명시적 누락 검사·Editor 검증 중 실제 필요한 보호만 적용한다.

### 1.7 무한형 맵의 생성·재활용 검토 [보류]

<a id="endless-map"></a>

- **문제**
	- 첫 맵은 제한형으로 유지하며 무한형 맵은 포스트-MVP 후보로 남아 있다.
	- 엔드리스 런 규칙과 공간의 무한 확장은 별개다.

- **전략**
	- 제한형 맵의 코어 전투를 확인한 뒤 작은 프로토타입을 검토한다.
	- Codex 제안: 공간 조각 재활용, 적·무기의 스폰/제거 범위, 길·건물 연결, 장거리 좌표 정밀도·내비게이션을 비교한다.
	- ArenaBounds에 동작을 선행 추가하지 않고 맵 유형별 책임의 실제 차이부터 확인한다.

### 1.8 자동 카메라 접근과 건물 페이드 검토 [보류]

<a id="camera-fade-and-damping"></a>

- **문제**
	- 자동 근접 시 장애물과 카메라 이동의 관계가 사용자에게 명확하지 않을 수 있다는 의견이 있었다.
	- 이는 실제 혼란의 관찰 결과나 자유 카메라 요청은 아니다.
	- 사용자는 2026-10-17에 맥락 전달·접근/복귀 감쇠·건물 페이드를 보류했다.

- **전략**
	- 현재 확대 정도와 주변 전투 공간을 확인해 보조 표현의 필요성을 판단한다.
	- 사용자 검토 방향은 가리는 건물의 불투명도 조절이며, 방법·수치는 미확정이다.

	| 후보 | 검토 내용 |
	|---|---|
	| 알파·디더·부분 마스킹 | 건물 단위 표시·깊이 정렬·그림자·복원·깜빡임 |
	| 접근·복귀 감쇠 | 장애물과 이동의 맥락·전환 속도·시야 확보 |
	| 조합 비교 | Codex 제안으로 대표 건물 한 채에서 비교, 대상 빌드 비용 확인 |

	- 페이드는 렌더링, 감쇠는 이동, Collider는 충돌을 담당하므로 역할을 구분한다.
	- 몸체·창문·간판·옥상 표시를 맞추고 투명해진 건물을 통행 가능한 길로 오해하지 않는지 확인한다.
	- 기준: [맵 디자인의 시야·카메라 기준](Design/MapDesign-KoreanFoodStreet.md#6-카메라-정책과-후속-과제). 기술 참고: [Dither](https://docs.unity3d.com/Packages/com.unity.shadergraph@17.0/manual/Dither-Node.html)·[Deoccluder](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/CinemachineDeoccluder.html)·[URP Lit](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/lit-shader.html).
	- 다른 게임의 페이드 기억은 사용자 경험이며 공식 구현 확인 사실로 취급하지 않는다.

### 1.9 PVP와 추가 스테이지 구상 [보류]

<a id="pvp-and-stages"></a>

- **문제**
	- 사용자는 물건 확보·교체 중심의 난투를 장기적으로 캐주얼 PVP와 여러 장소로 확장하고 싶다고 밝혔다.
	- 인원·승리 조건·맵 크기·플랫폼·네트워크 방식·추가 장소는 미확정이다.

- **전략**
	- 싱글플레이에서 물건 확보·교체·이동 판단을 확인한 뒤 확장을 검토한다.
	- PVP는 동시 픽업·공격 판정·상태 동기화 비용을 조사하고, 그 전에 네트워크 구조를 도입하지 않는다.
	- 추가 스테이지는 장소별 물건과 전투 공간이 다른 판단을 만드는지 비교한다.

### 1.10 적의 원거리 공격과 현장 무기 활용 [보류]

<a id="enemy-ranged-and-pickup"></a>

- **문제**
	- 물건 투척·새총·폭죽·개조 발사기 등의 적 후보에는 원거리 공격과 현장 물건 확보라는 서로 다른 행동이 필요하다.
	- 사용자는 2026-10-19에 무기 준비·역할 확인을 먼저 하고 적 확장을 유보했다.

- **전략**
	- 기본 펀치·공통 장착 기반을 유지하고 무기 역할 확인 후 원거리 견제형·현장 무기 활용형을 검토한다.
	- 공격 거리·투사체·준비 동작·주기·거리 유지 규칙은 채택 시 정한다.
	- Codex 제안: 준비된 무기를 쓰는 원거리 적과 바닥 무기를 찾아 확보하는 AI를 나누어 검토한다.
	- 고정 장비의 표현과 실제 물건 탐색·동시 픽업·사용 행동을 구분한다.
	- 플레이어 장착 물건 투척·배경 물체 집기/파괴도 별도 미확정 후보로 남긴다.
	- 외형·성격 후보는 [EnemyDesign](Design/EnemyDesign.md#6-후속-후보와-열린-질문)을 참고한다.

### 1.11 적 간 공격 유도와 반응 말풍선 [보류]

<a id="enemy-friendly-fire-and-bubbles"></a>

- **문제**
	- 사용자는 위치 선정으로 적의 공격이 다른 적에게 맞는 상황과 그 결과를 드러내는 말풍선을 제안했다.
	- 실제 적 간 피해·경직을 허용할지 피격 표현만 쓸지는 미확정이다.

- **전략**
	- 개별 공격의 기본 대응을 확인한 뒤 공격 유도·말풍선을 함께 검토한다.
	- 도발과 피격 반응을 구분하고 발동 조건·빈도·동시 표시 수·공격 예고의 가독성을 정한다.
	- 대사 후보: "이 녀석 덤벼라!", "아잇! 아프잖아!", "어떤 자식이 아군을 때리냐?!"
	- 대상 공격·피해량·피해 대상 규칙은 채택 시 별도로 정한다.

### 1.12 적 역할별 협동·진형 전술 [보류]

<a id="enemy-group-tactics"></a>

- **문제**
	- 사용자는 적 역할별 협동·진형·접근 전략을 장기 후보로 제안했다.
	- 기존 슬롯 포위·자리 예약만으로 집단 전술이 구현된 것은 아니다.

- **전략**
	- 개별 근접·원거리·현장 무기 활용 적의 대응 차이를 확인한 뒤 역할 분담·진형·접근 전략을 검토한다.
	- 전술 종류·역할 수·동시 행동 제한·조율 방식을 구체화한다.
	- 기존 무기·적 작업보다 먼저 새 AI 구조를 도입하지 않으며 군대 테마 채택과도 구분한다.
