## 0. 일러두기

1. **범위.**
	- 문서 체계의 구조와 원칙만 담는다.
	- 게임/Unity 특화 내용은 배제한다.
2. **`WritingGuide.md`와의 관계.**
	- 이 문서는 `WritingGuide.md`의 공식 대상 문서(`GDD.md`/`DevPlan.md`/`Systems.md`)가 아니다.
	- 사용자 요청으로 `WritingGuide.md`의 전 규칙을 이 문서에도 적용했다.
3. **출처 구분.**
	- 1장은 이 프로젝트에 실제로 존재하는 각 문서의 최상단 서술을 그대로 요약/발췌한 사실이다.
	- 2장과 4장은 그 사실들로부터 Claude가 일반화해 도출한 원칙/제안이며, 사용자의 확정 검토를 거치지 않았다.

## 1. 문서 목록과 역할

이 체계는 문서를 세 축으로 나눈다. 'WHAT'(무엇을 만드는가, 스펙/범위)은 지금 확정된 것만 남기고, 'WHEN'(어떤 흐름으로 구현하는가, 작업별 순서)은 WHAT과 분리해 범위 변경 없이 순서만 바꿀 수 있게 하며, 'HOW'(어떻게 만들었는가, 구현 결정의 경위)는 뒤집혀도 지우지 않고 쌓는다. 여기에 미루기 공간(Backlog), 세션 간 인수인계(Handoff), 1회성 논의 초안(DiscussionDraft), 시행착오 탐색 로그(Troubleshooting)가 보조로 붙는다.

| 문서 | 축 | 성격 | 편집 방식 |
|---|---|---|---|
| `GDD.md` | WHAT | 규칙/스펙의 단일 진실 공급원 | 확정된 것만 남기고 덮어씀 |
| `Systems.md` | WHAT | 범위 체크리스트, 우선순위 없음 | 확정된 것만 남기고 덮어씀 |
| `DevPlan.md` | WHEN | 작업 묶음별 구현·확장 순서 | 합의한 작업 흐름을 반영하고 진행 상태는 기록하지 않음 |
| `DevNotes/` | HOW | 주제별 구현 결정 히스토리 | append-only, 스냅샷 누적 |
| `Backlog.md` | 미루기 | 보류 과제와 처리 흔적 | 순서 번호 갱신, 번호 없는 고정 앵커, 처리 결과 분리 |
| `HANDOFF.md` | 인수인계 | 이번 라운드 발췌 요약 | 라운드마다 전체 덮어씀 |
| `DiscussionDraft.md` | 임시 | 현재 요청의 논의·검토 초안 | 제목·일러두기 보존, 본문 교체 |
| `Troubleshooting/` | 탐색 로그 | 특정 문제의 시행착오 전체 | 번호가 붙은 문제별 파일, append 위주 |
| `WritingGuide.md` | 메타 | 위 문서들의 문체/서식 규칙 | 상시 참고 아님, 편집 시에만 로드 |

### 1.1 WHAT: 스펙 문서 (`GDD.md`, `Systems.md`)

- 지금 확정된 상태만 담는다.
	- 지나간 경위나 폐기된 대안은 여기 남기지 않는다.
- `GDD.md`는 규칙/동작의 상세 스펙이고, `Systems.md`는 범위 안에 있는 것을 빠짐없이 나열하는 평면 체크리스트다.
	- 둘 다 우선순위나 순서는 다루지 않는다.
- 다른 문서(`DevPlan.md`/`DevNotes/`)의 존재나 개발 단계 번호를 언급하지 않는다.
	- 시점 표현이 필요하면 'MVP 포함'/'후순위'/'범위 밖' 같은 상태 표현을 쓴다.
	- 이렇게 하면 스펙 문서가 진행 상황과 결합되지 않아 독립적으로 읽힌다.

---

### 1.2 WHEN: 순서 문서 (`DevPlan.md`)

- 주요 작업을 묶고 각 묶음의 구현·확장 순서를 정리한다.
	- 묶음의 배열을 프로젝트 전체의 강제 단계로 사용하지 않고 독립 작업은 병행할 수 있다.
	- 묶음을 가로지르는 중요한 합의 순서만 짧게 남긴다.
- 기능 범위·상세 규칙은 Systems·GDD를 따르고, 진행 상태·구현 경위·검증 수준은 반복하지 않는다.
- 구현 세부와 결정 이유는 `DevNotes/`의 관련 기록에 남기며, DevPlan에는 필요한 작업 흐름만 유지한다.

---

### 1.3 HOW: 결정 히스토리 (`DevNotes/`)

- WHAT/WHEN 문서와 정반대 성격이다.
	- WHAT/WHEN 문서는 폐기된 개념을 지우지만, 이 문서는 '그 당시엔 이렇게 판단/논의했다'는 경위 자체가 보존 대상이라 나중에 틀린 것으로 밝혀진 판단도 지우지 않는다.
- 스냅샷 축적 문서다.
	- 각 섹션은 그 시점에 확정된 결정의 기록이다.
	- 뒤집히거나 정정돼도 당시 설명과 사유를 고쳐쓰지 않고 새 섹션을 추가해 남긴다.
- 새 결정이 이전 기록을 변경·폐기하면 영향을 받는 절의 제목 아래에 '후속 변경' 안내를 덧붙인다.
	- 변경 범위를 `[일부 변경]`·`[대체됨]`·`[폐기됨]`으로 구분하고 최신 기록으로 연결한다.
	- 일부 변경은 바뀐 내용만 명시하고, 과거 검증을 변경 후 동작의 검증으로 해석하지 않도록 안내한다.
	- 재변경 시 관련 안내를 최신 결론으로 갱신하되 당시 본문·제목·앵커는 보존한다.
	- 작업 마무리 시 이번 변경에 관련된 기록만 확인한다.
	- 상세 작성 절차는 `DevNotes/README.md` 0장 7번을 따른다.
- 실제 코드와 내용이 어긋나면 코드가 우선이다.
	- 다만 기존 섹션을 바로 고치지 않는다.
	- 그 차이를 이미 반영한 더 나중 섹션이 있는지 먼저 확인하고, 없으면 새 섹션을 추가한다.
- 기록은 한 파일에 계속 누적하지 않고 의미 있는 주제 단위의 파일로 나눈다.
	- `DevNotes/README.md`는 공통 작성 규칙과 파일 색인을 보관한다.
	- 기록 파일은 `NN-Topic.md` 형식으로 만들고, 파일 번호와 내부 `## N` 번호를 맞춘다.
	- 번호는 개발 단계가 아니라 기록 묶음의 생성 순서를 뜻한다.
- 기록을 편집하기 전에 `DevNotes/README.md`와 대상 기록 파일을 함께 읽는다.

### 1.4 미루기 공간 (`Backlog.md`)

- **역할**
	- 사용자가 다시 다룰 일로 정한 기획·기술 과제를 보존한다.
	- 기존 개발 계획의 작업·아이디어·미검증 사항을 자동으로 별도 과제로 만들지 않는다.
- **등록**
	- 신규 등록·재등록·범위 확대는 백로그라는 보존 위치를 명시한 사용자 요청 또는 백로그 등록안에 대한 명시적 동의가 있을 때만 한다.
	- AI 제안은 대화에서 먼저 검토하고, 새 항목에는 사용자 요청일·요청 요지를 남긴다.
	- 아이디어·개발 방향·어딘가 기록하자는 요청·문서 이관·편집 승인은 백로그 등록 승인이 아니며, 과거 제외 항목을 임의로 되살리지 않는다.
- **작성**
	- 미결 과제는 문제·전략으로 작성하고 중요한 선행 조건만 내용에 포함한다.
	- 상세 구현 이력은 필요한 보존 기록으로 연결한다.
- **식별과 처리**
	- 보류 과제는 하나의 H2 아래 H3로 나누고 표시 번호를 문서 순서에 맞춰 갱신한다.
	- 참조는 번호·상태와 무관한 고정 앵커를 사용하며 링크 이름에는 과제명을 적는다.
	- 미결 과제는 [보류]·[착수]로 표시한다.
	- 실제 관리한 과제의 완료·철회 결과는 별도 H2의 처리 표에 제목·상태·처리일·짧은 결과와 필요한 기록 링크를 남긴다. 처리 결과가 없으면 해당 장을 만들지 않는다.
	- 등록 자체가 취소되거나 완전 삭제를 요청받은 항목은 본문·처리 표·앵커에서 제거하고 관련 참조를 정리한다. 과거 본문은 Git 이력으로 확인한다.
	- 장기적인 결정·실패 원인만 DevNotes에 보존한다. 등록 취소를 기능의 영구 기각이나 검증 완료로 해석하지 않는다.
	- 문서 개편 이력은 마지막 H2에서 관리한다.

### 1.5 인수인계 (`HANDOFF.md`)

- 세션 간 공통 인수인계 문서다.
	- 신규 의사결정을 기록하지 않고, WHAT/WHEN/HOW 문서에 이미 확정된 내용 중 이번 라운드에 필요한 것만 발췌해 전달한다.
- 작업 세션은 마무리할 때 다른 세션에 필요한 변경 결과·확인한 검증·생략하거나 남은 검증을 짧게 반영한다.
- 현재 작업의 진입점으로 안내할 수 있지만, 본문·특정 절을 영구 근거로 참조하지 않는다.
	- 계속 참조할 내용은 기준 문서나 `DevNotes/` 등에 보존한 뒤 그 위치로 연결한다.
- 보존 문서가 아니다.
	- 매 라운드 전체 덮어쓰기가 가능하다.
	- 과거 라운드 이력이 필요하면 `DevNotes/`(확정된 결정)나 `Backlog.md`(보류 중인 후보)를 본다.
	- 버전·수정일·문서 내부 변경 이력은 두지 않고, Git 이력으로 과거 본문을 확인한다.
	- `0. 일러두기`, `1. 이번 작업`, `2. 현황`, `3. 다음 작업`, `4. 관련 문서` H2를 유지한다.
	- `1.1 목표`, `1.2 필요한 결정`, `1.3 제외 범위`, `2.1 구현`, `2.2 확인`, `2.3 미확인`, `3.1 시작 조건`, `3.2 작업 순서`, `3.3 완료 판단`, `4.1 기준 문서`, `4.2 구현 기록`, `4.3 보류 항목` H3를 유지한다.
	- 고정 H2/H3는 사용자의 명시적 요청 없이는 수정·삭제하지 않고, 새 분류가 필요할 때만 해당 H2 아래에 H3를 추가한다.
	- `4. 관련 문서`는 문서 하나를 표 행 하나 또는 불릿 하나로 기록하고, 해당 문서의 확인 목적을 한 문장으로 적는다.
- 예외적으로, 신규 설계 판단이 이번 라운드의 목적 자체인 경우 미확정 안건을 그대로 담을 수 있다.
	- 확정된 결정은 적합한 보존 문서로 옮긴다. Backlog로의 이관은 사용자의 명시적 백로그 등록 요청이 있을 때만 한다.
- 구현 세션이 작업 중 새로운 설계/아키텍처 결정을 하게 되면, 완료 보고에 일단 적더라도 다음 라운드 시작 전에 반드시 `DevNotes/`(범위 변경이면 `DevPlan.md`)로 승격시킨다.
	- `HANDOFF.md`에만 남겨두지 않는다.

### 1.6 논의·검토 초안 (`DiscussionDraft.md`)

- 사용 중인 한 작업 세션만 읽고 쓰는 비영구 메모다.
	- 현재 요청의 검토, 선택지, 제안, 구현 초안과 작업 중 메모를 정리한다.
	- 다른 세션은 이 파일을 읽거나 수정하지 않고 `HANDOFF.md`와 보존 문서에서 공통 정보를 확인한다.
	- 다른 문서에서 본문·특정 절을 참조하거나 읽도록 안내하지 않는다.
	- 역할 안내에 파일명을 적는 것은 허용한다.
- 여러 라운드를 누적 보존하지 않는다.
	- 문서 제목과 `0. 일러두기`는 고정 운영 규칙으로 유지한다.
	- 새 요청이 들어오면 `## 1` 이후의 이전 내용은 삭제되고 이번 요청의 내용으로 교체된다.
	- 항상 사용 중인 세션의 '가장 최근 요청 하나'만 담는다.
	- 질문/답변이 길어 대화 출력만으로 가독성이 떨어지거나, 사용자가 명시적으로 정리된 문서를 요청했을 때만 쓴다.
	- 본문은 교체되지만 VCS에는 포함해 당시 논의와 판단 맥락을 보존한다.
	- 버전·수정일·문서 내부 변경 이력은 두지 않고, Git 이력으로 이전 초안을 확인한다.
	- `0. 일러두기`, `1. 이번 요청`, `2. 작업 계획`, `3. 작업 결과`, `4. 관련 문서` H2를 유지한다.
	- `1.1 목표`, `1.2 작업 맥락`, `1.3 필요한 결정`, `1.4 제외 범위`, `2.1 작업 내용`, `2.2 검토한 대안`, `2.3 작업 절차`, `2.4 변경 범위`, `2.5 검증 기준`, `3.1 변경 요약`, `3.2 사용자 확인`, `3.3 검증 결과`, `4.1 기준 문서`, `4.2 조사·작업 기록`, `4.3 보류 항목` H3를 유지한다.
	- 고정 H2/H3는 사용자의 명시적 요청 없이는 수정·삭제하지 않고, 새 분류가 필요할 때만 해당 H2 아래에 H3를 추가한다.
	- `4. 관련 문서`는 문서 하나를 불릿 하나로 기록하고, 해당 문서의 확인 목적을 한 문장으로 적는다.
- 초안 단계의 계획도 여기 먼저 쓰고 검토받는다.
	- 확정되지 않은 계획을 곧바로 `HANDOFF.md`나 `DevNotes/`에 쓰지 않는다.
	- 확정 뒤에는 현재 스펙을 `GDD.md`/`Systems.md`/`DevPlan.md`에, 구현 결정은 `DevNotes/`에, 구현 지시는 `HANDOFF.md`에 이관한다.

### 1.7 시행착오 로그 (`Troubleshooting/`)

- `DevNotes/`가 '최종 결정과 그 이유'만 남기는 것과 달리, 결정에 도달하기까지 밟았던 길 전체(막다른 길 포함)를 분기별로 남긴다.
	- 같은 막다른 길을 다시 밟는 시간 낭비를 막는 게 목적이다.
- 여러 세션/도구에 걸쳐 흩어진 시행착오 기록을 하나의 파일로 취합하기에 적합하다.
- `DevNotes/`처럼 '결정 단위'로 압축하지 않는다.
	- 검토한 선택지, 왜 막혔는지, 다음에 뭘 시도했는지를 순서대로 남기는 게 핵심이라 오히려 장황해도 된다.
- 프로젝트 전역이 아니라 특정 문제 하나에 국한된 로그이므로, 문제별로 파일을 분리한다.
- `Troubleshooting/README.md`는 공통 작성 규칙과 파일 색인만 보관한다.
	- 실제 조사 기록은 생성 순서에 따라 `NN-Topic.md` 형식으로 번호를 붙인다.
	- 파일 번호는 개발 단계 번호가 아니며, 내부 `##` 번호는 각 조사 문서에서 1부터 독립적으로 시작한다.
- 로그를 편집하기 전에 `Troubleshooting/README.md`와 대상 기록 파일을 함께 읽는다.
- 확정된 주요 기술 결정은 `DevNotes/`에 압축해 이관하되, 조사 경로는 원래 로그에 보존한다.

### 1.8 작성 스타일 가이드 (`WritingGuide.md`)

- 프로젝트의 구조화된 Markdown 문서를 쓰거나 정리할 때 기본 적용하는 문체/서식 규칙이다.
	- 상시 참고 문서가 아니라 문서 편집 작업을 할 때 불러와 쓴다.
- 문서 성격상 맞지 않는 규칙은 대상 문서의 `0. 일러두기`에서 적용 범위와 이유를 명시한 경우에만 예외로 둔다.
	- `DevNotes/README.md`가 append-only 기록에 맞는 채택 규칙과 예외를 따로 선언한 것이 해당 사례다.
- 핵심 원칙: 중복 방지(같은 사실은 홈 챕터 한 곳에만, 다른 곳은 교차 참조), 사유 보존(삭제하지 않되 압축), 히스토리와 스펙 분리(본문은 확정된 것만, 경위는 별도), 출처 구분(AI 제안인지 사용자 결정인지 항상 구분).

## 2. 핵심 설계 원칙

1. **단일 진실 공급원(Single Source of Truth).**
	- 하나의 사실/결정은 그 주제의 '홈' 문서 한 곳에만 자세히 쓴다.
	- 다른 문서에서 필요하면 전체를 재서술하지 않고 짧게 교차 참조한다.
2. **확정 vs 히스토리 분리.**
	- '지금 뭐가 맞는가'를 담는 문서(WHAT/WHEN)와 '왜 그렇게 됐는가'를 담는 문서(HOW)를 나눈다.
	- 전자는 덮어쓰기, 후자는 append-only로 편집 방식 자체를 다르게 가져간다.

3. **보존 문서 vs 비영구 문서 구분.**
	- 각 문서를 만들 때 '쌓이는 기록인가, 매번 교체되는 스냅샷인가'를 먼저 정한다.
	- 비영구 문서(`HANDOFF.md`/`DiscussionDraft.md`)를 보존 문서처럼 쓰면 언젠가 지워질 결정이 거기에만 남아 유실된다.
4. **이관 트리거를 명시한다.**
	- '이 상태가 되면 저 문서로 옮긴다'를 각 문서 상단에 규칙으로 적어 둔다.
	- 예: `DevPlan.md` 항목이 구현 세부로 비대해지면 `DevNotes/`로, `Backlog.md` 항목이 착수·완료·폐기되면 확정 기록을 `DevNotes/`에 보존하고 처리 표에는 짧은 결과와 기록 링크를 남긴다. 등록 취소·완전 삭제는 참조까지 제거한다.
	- 규칙이 없으면 중복/누락이 반복해서 발생한다.
5. **사유는 삭제하지 않는다.**
	- 결정 이유가 없으면 나중에 같은 논쟁이 반복되거나 이미 기각된 안이 재제안된다.
	- 다만 장황하게 늘어놓지 않고 압축한다.
6. **출처를 구분한다.**
	- AI와 협업하는 문서 체계에서는, AI가 제안한 문장인지 사용자 본인이 결정한 것인지 항상 구분해서 표시한다.
	- 동의받기 전에는 조용히 문서에 흡수시키지 않는다.
7. **각 문서 최상단에 자신의 역할과 경계를 명시한다.**
	- 이 문서가 뭘 담당하고 뭘 안 담당하는지를 스스로 설명하게 한다.
	- 이게 있어야 나중에 어느 문서에 뭘 적어야 할지 헷갈리지 않는다.

## 3. 워크플로우 예시

```
[기획 세션]                         [구현 세션]
   |                                    |
   |-- GDD/Systems/DevPlan 갱신 -->     |
   |-- HANDOFF.md 작성(발췌) -------->  |-- HANDOFF.md 먼저 읽고 시작
   |                                    |-- 구현
   |                                    |-- 신규 결정 발생 시 HANDOFF
   |                                    |   완료 보고에 임시 기록
   |   <-- 완료 보고 반영              |
   |-- 완료 보고의 신규 결정을          |
   |   DevNotes/(HOW)로 승격             |
   |   또는 명시적 등록 요청 후 Backlog로 이관    |
   |-- HANDOFF.md 다음 라운드용으로     |
   |   덮어씀                          |
```

> `HANDOFF.md`는 '지금 세션에 필요한 것만' 담는 얇은 창구다. 실제 지식은 항상 WHAT/WHEN/HOW 문서로 되돌아가며, `HANDOFF.md`가 지식의 최종 저장소가 되지 않도록 라운드마다 정리한다.

## 4. 이식 체크리스트

1. **WHAT/WHEN/HOW를 최소 세 문서로 분리한다.**
	- 프로젝트 성격에 따라 이름은 바뀌어도 된다(`GDD.md` 대신 `Spec.md`, `DevPlan.md` 대신 `Roadmap.md` 등).
	- 이름이 아니라 '확정 스펙/순서/구현 경위'가 서로 다른 문서라는 게 중요하다.
2. **각 문서 최상단에 자기 역할과 경계를 1~2문단으로 적는다.**
	- 특히 '여기 안 쓰는 것'을 명시하면 나중에 오염을 막기 쉽다.
3. **`Backlog.md`를 처음부터 만든다.**
	- 'TODO 주석으로 남기고 나중에 정리' 패턴은 결국 흩어져서 유실된다.
	- 배경/전략 3단 구조를 처음부터 강제하면 재조사 비용이 줄어든다.
4. **여러 세션/에이전트를 오가며 작업한다면 `HANDOFF.md`를 둔다.**
	- AI 협업이 아니어도, 사람 간 인수인계(온보딩, 교대 근무)에도 같은 구조가 적용된다.
5. **`DevNotes/`의 공통 규칙과 색인을 `README.md`에 둔다.**
	- '정정됐다고 기존 섹션을 고쳐쓰지 않는다'는 append-only 규칙이 없으면 결국 경위가 지워진다.
	- 기록이 길어지면 의미 있는 주제 단위로 나누되, 파일마다 규칙 전문을 반복하지 않는다.
6. **길게 이어지는 개별 문제의 시행착오는 별도 폴더(`Troubleshooting/`)로 분리한다.**
	- `DevNotes/`에 섞으면 결정 로그가 장황한 탐색 기록으로 오염된다.
	- 공통 규칙과 색인은 `README.md`에 두고, 실제 로그는 번호가 붙은 문제별 파일로 나눈다.
7. **문서 작성 스타일 규칙은 필요해질 때 `WritingGuide.md`류 문서로 뺀다.**
	- 처음부터 만들 필요는 없다.
	- 편집 중 즉흥적으로 지킨 규칙이 쌓이기 시작하면 그 시점에 분리한다.
8. **비영구 문서(`DiscussionDraft.md`)도 VCS에 포함한다.**
	- 매번 전체 교체되는 본문과 별개로, 커밋 이력은 당시 논의와 판단 맥락을 보존한다.
