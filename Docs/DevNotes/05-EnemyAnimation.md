## 5. 적 캐릭터와 전투 표현

### 5.1 대표 적 모델 교체와 프리팹 통일

<a id="51-대표-모델과-적용-범위"></a>

<a id="56-대표-적-프리팹-통일"></a>

> 일자: 모델 교체 2026-10-13~14, 프리팹 통일·기록 2026-10-14

- **문제**

	- 기존 범용 적의 전투 구성을 유지하면서 새 대표 모델과 선택 공격·퇴장 클립을 연결할 기반이 필요했다.

- **결정**

	- Enemy_Grunt_01 프리팹에 Humanoid 모델과 기존 Idle·Running을 연결했다.
	- Root Motion을 끄고 모델 높이 2m·몸체 반경 0.5m·높이 2m를 유지했다.
	- 기존 Enemy_Basic은 최초 교체 때 보존했다.
	- 적용 직전 미저장 씬 배치를 보존하고 스포너의 프리팹 참조만 바꿨다.
	- 최초 교체 후에는 Enemy_Basic을 삭제하고 씬 제작 도구도 Enemy_Grunt_01을 사용하도록 통일했다(2026-10-14). 대표 프리팹이 없으면 씬 정리 전에 중단하도록 했다.

- **근거**

	- 외형 교체와 피해·이동 규칙 변경을 분리하고 실제 클립은 나중에 선택하도록 했다.
	- 대표 프리팹의 사용 대상을 단일화하고, 리소스 누락 상태에서 파괴적인 씬 재생성을 피했다.

- **검증과 한계**

	- 유효 Avatar·SkinnedMeshRenderer 한 개·URP Lit 재질 연결을 확인했다. 실제 사용자 공격·퇴장 클립과 대상 빌드 성능은 미검증이었다. 공격 정책은 5.29, 기본 펀치는 5.33을 따른다.
	- 프리팹 통일 때 저장 에셋·열린 스포너의 이전 참조 부재와 선택 메서드 반환값을 확인했다. 삭제 전후 GameScene·새 대표 프리팹은 동일했다. Play·전체 씬 재생성은 실행하지 않았다.

### 5.2 적의 사망·퇴장·풀 재사용 분리

<a id="52-전투-처리와-표현의-연결"></a>

<a id="53-중요한-코드-검토-안내"></a>

<a id="55-검증-결과와-한계"></a>

<a id="57-공격-재생-연결-보류"></a>

<a id="54-이후-클립-적용-절차"></a>

<a id="513-collider-상태-관리의-의도-명시"></a>

> 일자: 사망·퇴장 연결 2026-10-13~14, 공격 재생 제거·Collider 정리 2026-10-14~15, 후속 회귀 2026-10-16

- **문제**

	- 적의 사망 판정·보상과 퇴장 표현·풀 반납을 분리하면서 재사용 때 이전 상태가 남지 않게 해야 했다.

- **결정**

	| 시점 | 처리 |
	|---|---|
	| 당시 접촉 피해 | 기존 피해 뒤 DamageApplied로 공격 표현 요청 |
	| 사망 확정 | 추격·Collider·접촉 피해·간격 계산·체력바 종료 |
	| 보상·집계 | 사망 때 XP와 처치 통보 |
	| 퇴장 | 클립이 없으면 즉시, 있으면 표현 뒤 반납 |
	| 재사용 | 체력 초기화 뒤 이동·전투·표현 상태 복원 |
	| 비활성화 | 이벤트 구독·코루틴 정리 |

	- 정상 퇴장은 클립 길이를 대기 상한으로 삼고 일시정지는 게임 시간과 함께 멈췄다.
	- 2026-10-14에는 피해 적용 후 공격 클립을 재생하던 DamageApplied 이벤트·구독·연결을 제거했다. 당시 접촉 피해·이동·퇴장·재사용은 유지하고 준비용 공격 슬롯·상태만 남겼다.
	- 2026-10-15에는 Collider 상태의 최초 보관·사망 비활성화·재사용 복원을 CacheInitialColliderStates·DisableColliders·RestoreColliders로 구분했다. 비활성 자식을 포함해 저작 당시 상태를 복원하며 모든 Collider를 일괄 활성화하지 않는다.

- **근거**

	- 죽은 적이 퇴장 동안 전투에 참여하거나 표현 길이가 처치 집계를 늦추지 않게 했다. ReturnEnemy는 실제 반납만 담당하도록 분리했다.
	- 피해를 먼저 적용한 뒤 공격 클립을 재생하면 타격 프레임과 피해 시점이 어긋난다. 공격 시작·타격 시점·범위 재확인·헛공격 규칙을 정하기 전에는 표현만 연결하지 않기로 했다.
	- Collider 정리는 저장된 초기 상태를 복원한다는 계약을 코드의 작업 이름으로 드러내기 위한 변경이었다.

- **검증과 한계**

	- 컴파일과 별도 Play 씬의 22개 항목에서 추격·접촉 피해 8·쿨다운·공격 레이어 제외·빈 클립·선택 퇴장·즉시 보상·일시정지·반복 재사용을 확인했다.
	- 다섯 생애에서 처치 5·XP 50을 확인했고 게임 씬 사본의 적 다섯 명·체력바도 확인했다.
	- 초기 검사는 백그라운드 정지·Animator 전환 대기 때문에 실패해 실제 갱신을 기다리도록 보정했다.
	- 실제 사용자 클립·직접 전투·대상 빌드·최종 아트는 미검증이었다.
	- 초기 공격 재생 검사는 연결 제거 전 결과이며, 실제 손 타격 창과 공통 모션 적용은 5.33에 기록했다.
	- 2026-10-14 공격 재생 연결 제거 후 컴파일은 오류·경고 없이 완료했고 Play는 재검증하지 않았다. 과거 Inspector 공격 슬롯 연결만으로 공격이 재생되는 절차는 현재 지침으로 사용하지 않는다.
	- 2026-10-15 Collider 정리는 컴파일과 기존 실행 순서 대조까지 확인했다. 당시 연결 중단으로 Play는 하지 못했고 2026-10-16의 5.15 회귀에서 Collider 복원을 확인했다. 당시 대표 프리팹은 루트 Trigger CapsuleCollider 하나였다.

### 5.8 대상 주변 슬롯 예약과 추종 분리

<a id="58-대상별-슬롯과-추종-분리"></a>

> 일자: 2026-10-15

- **문제**

	- 대상 주변 자리 배정과 이동을 분리하고 공통 AI 부모 없이 같은 슬롯 기능을 사용해야 했다.

- **결정**

	| 구성 | 당시 책임 |
	|---|---|
	| SurroundSlots | 대상별 자리·예약·대기 |
	| SlotFollower | 추종 상태·실제 이동·환경 검사 |
	| EnemyAI | 타깃·사망·재사용 연결 |

	- Join·Query·Leave·Retry에서 대상·참여 생애와 revision을 확인하고 비활성화 때도 예약을 반환하도록 했다.

- **근거**

	- 게임 개체와 슬롯 기하를 분리하고 오래된 예약 응답이 새 생애를 바꾸지 않도록 했다. 복구 불가능한 겹침에서는 재등록을 반복하지 않고 안전 위치를 기다렸다.

- **검증과 한계**

	- 컴파일과 격리 Play 33개·전투 5개 항목, 게임 씬 사본의 4명 도착·4명 대기를 확인했다.
	- 첫 반경 0.9m·도착 0.03m에서는 실제 접촉 이벤트가 없어 0.85m·0.015m로 줄였다.
	- 64명 단일 Editor 표본은 평균 프레임 17.6ms·최대 28.1ms였으며 전후 CPU·할당 비교나 대상 빌드 보장이 아니다.
	- 책임은 5.10·5.15, 이동 방식은 5.30에서 변경했다.

### 5.9 커서 위치의 다수 적 생성 도구

<a id="59-커서-주변-적-일괄-생성-테스트"></a>

> 일자: 2026-10-15

- **문제**

	- 다수 적의 포위·대기·풀 재사용을 커서 위치에서 반복 확인할 도구가 필요했다.

- **결정**

	- Editor Play의 Game 뷰에서 F8로 기본 20명, Inspector에서 1~100명을 요청하도록 했다.
	- DebugEnemySpawn이 커서·경계·환경·점유를 확인하고 실제 생성은 기존 SpawnAt 경로를 사용했다.
	- 키 유지·일시정지·UI·화면 밖·대상 사망에서는 생성하지 않았다.
	- 공간 부족 때 가능한 자리만 채우고 실제 생성 수를 알렸다.
	- 배포에는 입력·배치 코드를 포함하지 않았다.

- **근거**

	- 스포너가 디버그 키·마우스·슬롯을 알지 않도록 하고 정상 스폰과 같은 초기화·보상·풀 계약을 재사용했다.

- **검증과 한계**

	- 컴파일·격리 Play 23개와 게임 씬 사본의 F8 20명·슬롯 추종을 확인했다.
	- 공간 부족 10/20명·최소 간격 약 1.1m, 재사용 HP 30·XP 10·처치 1을 확인했다.
	- 배포 심볼 컴파일에서 테스트 실행 메서드가 제외됨을 확인했다.
	- 검증은 당시 평면 바닥·대표 적 몸체 기준이며 후속 이동은 5.30을 따른다.

### 5.10 이동·환경 검사의 책임 분리와 안전한 적 생성

<a id="510-슬롯ai-이동-책임-분리와-안전한-스폰"></a>

> 일자: 2026-10-15

- **문제**

	- 건물 내부 자동 스폰을 차단하고 자리 관리·실제 이동·환경 검사의 책임을 나눠야 했다.

- **결정**

	| 구성 | 당시 책임 |
	|---|---|
	| SurroundSlots | 자리·예약·대기·충원 |
	| SlotFollower | Goal·증표·도착 상태, 직접 이동 제거 |
	| EnemyAI | 실제 이동·분리·충돌·진전·안전 복귀 |
	| EnvironmentQuery | 캡슐·경계·겹침·이동 검사 |
	| SpawnAt | 바닥·경계·환경·캐릭터 검사 뒤 풀 사용 |

	- Ground·WorldObstacle을 분리하고 자동 스폰 후보는 최대 30회 시도하도록 했다.

- **근거**

	- 안전하지 않은 위치는 활성화 전에 거절하고 슬롯 계산은 실제 맵·물리에서 분리했다. F8도 같은 SpawnAt 검사를 사용하게 했다.

- **검증과 한계**

	- 컴파일과 80개 항목에서 슬롯·전투·F8·실제 맵 안전 스폰을 확인했다.
	- 건물 내부 생성 차단, 자동 100주기 성공, 실패 조건의 30회 상한을 확인했다.
	- 64명·100회 수동 갱신 CPU는 2.99→2.94ms였으나 단일 Editor 표본으로 개선을 단정하지 않았다.
	- GC 카운터가 1MiB 대조 할당도 0을 반환해 할당 결과는 폐기했다.
	- EnemyMovement 분리와 공통 이동 전환은 5.15, NavMesh 이동 방식은 5.30에 기록했다.

### 5.11 몸체 크기를 반영한 다중 링 슬롯

<a id="511-몸체-기반-다중-링-슬롯"></a>

> 일자: 2026-10-15

- **문제**

	- 단일 원이 차면 같은 대기 반경에 적이 모여 몸체 크기에 맞는 외곽 자리가 필요했다.

- **결정**

	- 대상 반경 Rt·참여 최대 반경 Ra·여유로 원별 슬롯 수를 계산했다.
	- 첫 반경은 max(0.01,Rt+Ra-Contact Inset), 다음 반경은 이전 반경+2Ra+Spacing이다.
	- 인접 직선 간격 2R·sin(π/n) ≥ 2Ra+Spacing을 만족하는 최대 정수를 사용했다.
	- 부족할 때만 바깥 원을 추가하고 안쪽 빈자리로 가능한 참여자를 승격했다.
	- 큰 몸체가 들어오면 참여 Ticket은 유지하고 슬롯 revision을 갱신했다.
	- 크기 정보가 없으면 예약을 보류하고 오래된 Goal은 거절했다.

- **근거**

	- 몸체 크기로 간격을 결정하면서 기존 예약을 불필요하게 흔들지 않기 위한 방식이었다. 슬롯은 기하·예약만 소유하고 물리·직접 이동은 소유하지 않게 했다.

- **검증과 한계**

	- 기본 Rt=Ra=0.5·Spacing 0.1·Inset 0.15에서 반경/개수는 0.85/4·1.95/10·3.05/17·4.15/23·5.25/29다. 최대 5원은 83자리, 내부 상한은 128이다. 컴파일·121개 항목, 64명 도착·최소 중심 간격 약 1.086m와 게임 사본 20명의 4·10·6 점유를 확인했다.

	| 당시 64명 표본 | 전 | 후 | 한계 |
	|---|---|---|---|
	| 100회 수동 이동 갱신 CPU 평균 | 3.61ms | 5.52ms | 동작이 다른 단일 Editor 표본 |
	| 전체 Play 프레임 할당 평균 | 약 25,334B·36표본 | 약 25,476B·29표본 | 렌더·UI·Editor 포함 |

	- Profiler 할당 카운터는 1MiB 대조를 통과했으나 이동 코드만의 무할당을 증명하지 않는다.
	- 2026-10-25: 사용자가 다중 링 관련 검증을 완료했다고 확인했다.
	- 이 결과는 5.30의 새 이동 방식 검증이 아니다.

### 5.14 적 생애주기 이벤트와 스포너의 풀 관리

<a id="514-적에서-스포너-참조-제거"></a>

> 일자: 2026-10-16

- **문제**

	- 적이 자신의 생성자의 처치 집계·풀·환경 정보를 직접 알 필요가 없었다.

- **결정**

	| 구성 | 책임 |
	|---|---|
	| EnemyAI | 전투 제외 뒤 Died, 표현 종료 뒤 ExitCompleted를 생애당 한 번 통보 |
	| EnemySpawner | 활성 대여 목록·구독·집계·반납 |
	| 이동 | 스포너가 경계를 직접 전달 |

	- 반납 때 구독을 해제하고 이미 반환된 적의 중복 반납을 무시하며 스포너 파괴 때 남은 구독도 정리했다.

- **근거**

	- 소유자인 스포너가 적의 생애 통보를 받아 처리하도록 의존을 뒤집었다. 2.23의 이벤트 대안에서 우려한 구독 누적을 대여 목록과 명시적 해제로 다뤘다.

- **검증과 한계**

- **검증과 한계**

	- 지역함수 정리는 변경 전후 조건·호출 순서와 컴파일을 확인했다. 씬·프리팹 변경과 Play 실행은 없었다(2026-10-18).
	- 크기·밝기 조정은 파티클 두 개·원래 재질·추가 링 제거·저장 수치를 확인했다. 사용자 조합 확인과 개별 자동 실행·대상 빌드·성능 검증은 구분한다.

### 5.29 적 유형별 공격에 따른 피해 판정

<a id="529-유형별-공격-피해-정책으로-전환"></a>

> 일자: 2026-10-19

- **문제**

	- 모든 적의 몸체 접촉 피해는 공격을 피한 뒤 접근·반격하는 기회와 충돌할 수 있었다.

- **결정**

	- 유형별 공격의 활성 상태·피해 조건을 정의하기로 했다. 몸체 충돌·개체 분리는 피해 판정과 구분하고, 확정 게임 규칙은 GDD 6.1에서 관리한다.

- **근거**

	- 접근·회피·반격의 판단을 적의 행동과 연결하기 위한 정책이었다. 초기 접촉 피해는 별도 공격이 없던 단계의 지속 접근 위험을 제공했다.

- **검증과 한계**

	- 사용자 기획을 확정했으며 당시 코드·씬 적용은 미착수였다. 기존 모델을 재사용하되 첫 유형의 패턴·예고·회복 수치는 당시 미확정이었다. 접촉 피해가 단조로움의 단독 원인이나 정책 효과를 입증한 것은 아니다. 기본 적의 구현은 5.33이며 과거 이동·풀·보상 검증 전체를 폐기하는 변경은 아니다.

### 5.30 NavMesh 경로 이동과 슬롯 추종 분리

<a id="530-navmesh-일반-이동과-역할-이름-전환"></a>

> 일자: 2026-10-19

- **문제**

	- 직접 이동은 장애물 앞에서 멈추며 우회 경로를 제공하지 않았다.

- **결정**

	| 구성 | 책임 |
	|---|---|
	| EnemyAI | 추종 의도·생애주기 |
	| SlotFollower | 기존 TargetFollower의 자리·목표·재시도 |
	| NavigationMovement | 기존 CharacterMovement를 대체, 목적지·회전·이동 상태 |
	| NavMeshAgent | 경로 이동·회피 |
	| SurroundSlots | 기하·예약·충원 |

	- 이동 상태는 Inactive·PathPending·Moving·Unreachable·OffNavMesh를 구분했다.
	- 새 예약은 이전 이동을 멈추고 요청하며 경로 계산 중에는 막힘 시간을 누적하지 않았다.
	- 풀 활성화 뒤 체력·표현 복원과 Agent 준비를 마친 후 추종을 시작했다.
	- 준비 실패는 구독 해제·풀 반환 후 null을 반환했다.
	- 사망 때 예약 반환·경로 삭제·Agent 비활성화로 회피 대상에서도 제외했다.

- **근거**

	- 직접 분리·Transform 이동을 표준 내비게이션으로 바꾸되 슬롯·추종·이동의 책임은 유지했다. 부분 경로 끝을 도착으로 오인하거나 정상 우회를 실패로 보지 않도록 했다.

- **검증과 한계**

	| 주요 설정 | 당시 값·조건 |
	|---|---|
	| 목적지 재요청 | 0.2초 간격·수평 0.1m 변화 |
	| NavMesh 검색·수평 보정 | 0.15m·최대 0.05m |
	| 막힘 재시도 | 유효 경로에서 0.05m/s 미만이 3초 지속 |
	| 도착·재추적·Agent 정지 거리 | 0.1m·0.2m·0.05m |
	| Agent | 반경 0.5·높이 2·속도 3.5·가속 40·Medium 회피 |
	| Surface | Ground·WorldObstacle, Volume 160×4×160, voxel 0.1 |

	- 컴파일·Missing Script 0·두 GUID 보존·저장 참조·베이크 연결과 기존 Transform·Collider 보존을 확인했다.
	- 장애물 57개는 Not Walkable로 표시했고 데이터는 Assets/Settings/Scenes/Navigation/GameSceneNavMesh.asset에 저장했다.
	- 지형 변경 시 Bake가 필요하다.
	- 베이크 기하 확인은 실제 우회·군집 검증이 아니다.
	- 예전 직접 이동 검증 도구는 그대로 재사용할 수 없고 전체 씬 빌더도 재실행하지 않았다.
	- 재구성 반복 문제는 5.31에서 수정했다.

### 5.31 반경 오차에 따른 슬롯 재구성 반복 방지

<a id="531-반경-계산-오차로-인한-슬롯-재구성-반복-수정"></a>

<a id="532-반복-정지-수정의-사용자-확인과-커밋"></a>

> 일자: 2026-10-19, 사용자 해결 확인 2026-10-19

- **문제**

	- 플레이어가 움직일 때 적이 정지·재출발을 반복했다. 미세한 반경 변화가 실제 크기 변경으로 처리됐다.

- **결정**

	- SurroundSlots의 대상 반경·최대 참여 반경과 SlotFollower의 참여 반경 비교 세 곳에 Mathf.Approximately를 적용했다. 무시한 차이는 기준값에 덮어쓰지 않아 실제 변화의 누적은 다시 비교하도록 했다.

- **근거**

	- 동일 프레임의 0.5→0.50000006 변화가 슬롯 재구성과 예약 revision 변경·이동 중단을 유발했다. 목적지는 멀고 경로가 유효했으며 재구성이 멈추면 정상 속도로 이동해 엄격 비교를 원인으로 좁혔다.

- **검증과 한계**

	- 수정 뒤 컴파일을 확인했고 이후 사용자가 반복 정지 해결을 확인했다. Agent·이동 수치·공격·씬은 바꾸지 않았다. 로그 재현 근거는 당시 로컬 RadiusTrace-before.log에 보존했다. 단일 적 우회·20/64명 군집·충원·재사용·전체 재시작·대상 빌드·성능의 개별 통과를 뜻하지 않는다.

### 5.33 공통 공격 경로를 사용하는 기본 적 펀치

<a id="533-공통-무기모션과-기본-적-펀치"></a>

<a id="534-공통-공격의-사용자-확인과-커밋"></a>

> 일자: 2026-10-19, 사용자 공격 확인 2026-10-19

- **문제**

	- 기본 적의 접촉 피해를 실제 펀치의 타격 창으로 교체하고 플레이어·적의 실행 경로를 공유해야 했다.

- **결정**

	- EnemyAI는 유효 목표·거리·공격 가능 상태를 확인하고 WeaponController.TryAttack을 요청했다.
	- 시작 거리 1.35m에서 슬롯 예약을 보존한 채 이동·막힘 재시도를 멈추고 방향을 확정했다.
	- 공격 종료 뒤 살아 있는 목표의 추종을 재개했다.
	- 무한 내구도 맨손·오른손 펀치 하나·피해 8·쿨다운 1초를 설정했다.
	- 원본 2초 클립의 손 타격 창 약 0.762~0.975초를 사용하고 공격속도에 맞춰 재생했다.
	- PlayerBody만 피해 대상으로 하고 EnemyAttack 레이어를 분리했다.
	- 사망·목표 변경·비활성화는 공격을 취소하고 재사용 때 손·명중·쿨다운·모션을 복원했다.

- **근거**

	- 플레이어 입력과 AI 판단은 분리하되 장착·타격·모션은 [공통 구조 3.31](03-PlayerAnimation.md#331-범용-무기와-사람형-모션-통합)을 사용했다. 실제 다음 공격은 쿨다운과 모션 종료를 모두 만족해야 하며 별도 예고·회복 타이머는 추가하지 않았다.

- **검증과 한계**

	- 컴파일·Missing Script 0·Humanoid·손 비활성·저장 후 씬 연결을 확인하고 기존 EnemyAnimationController·EnemyContactDamage를 제거했다. 첫 재공격 오류는 [3.32](03-PlayerAnimation.md#332-공격-상태-경로-이관-누락-수정)에서 수정했고 이후 사용자가 재공격·적의 실제 타격을 확인했다.

	| 확인 구분 | 결과·한계 |
	|---|---|
	| 사용자 확인 | 근접 재공격 정상·적 타격 정상 |
	| 사격 크래시 | 사용자 보고상 Unity 재시작 후 해소, 구체 원인 미확정 |
	| 미확인 | 교체·파괴·증강·업적·피해 횟수·벽·슬롯 접근·반복 재사용의 개별 회귀 |
	| 미구현 | 적 무기 탐색·획득 AI·벽 차단 추가 규칙 |
	| 별도 검증 | 자동 동작·대상 빌드·성능 |

	- 크래시 로그는 BlendTree의 네이티브 중단을 보였지만 상태 경로 수정을 크래시 원인 해결로 기록하지 않는다.
