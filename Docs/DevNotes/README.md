# 개발 노트: 공통 규칙과 색인

> 공개 편집본 p1 · 2026-10-23 · 원본 `703affa`. 현재 안내는 [공개본 문서 색인](../README.md)을 따른다. 과거 기록은 당시 상태이며 현재 코드 전체의 검증 결과가 아니다.

`DevPlan.md`는 '언제 무엇을 만들지'만 다루는 문서로 유지한다. 작업 중 확정되는 '어떻게 만들지'(컴포넌트 구조, 저장 방식 등 기술적 의사결정)는 이 폴더의 주제별 파일에 시간순으로 기록한다.

각 항목은 해당 시점의 결정 스냅샷이다. 실제 코드와 내용이 어긋나면 코드가 우선이다. 다만 기존 섹션을 고쳐 쓰지 않는다. 먼저 그 차이를 이미 반영한 더 나중 섹션이 있는지 확인하고, 없으면 해당 파일에 새 섹션을 추가해 갱신한다.

---

## 0. 일러두기

1. **스냅샷 축적 문서다.**
	- 각 섹션은 그 시점에 확정된 결정의 기록이다.
	- 뒤집히거나 정정돼도 당시 설명과 사유를 고쳐쓰지 않고 새 섹션을 추가해 남긴다.
	- 예외: 이전 기록에서 최신 결론을 찾을 수 있도록 '후속 변경' 안내를 덧붙인다(아래 7번).
	- 제목에는 날짜/상태 등 메타데이터를 넣지 않는다.
		- 제목 바로 아래 블록쿼트로 분리한다.
	- 메타데이터 필드는 해당하는 것만 쓴다: 일자 / 기록일 / 최초 설계 / 재확정 / 상태 / 참고 / 비고 / 후속 변경.
	- 확정 여부가 불확실하면 `> 상태: placeholder`처럼 명시한다.

2. **`WritingGuide.md`를 기본으로 적용하되, 이 문서의 성격에 맞는 명시적 예외를 둔다.**
	- 아래 적용 범위와 예외는 2026-08-08에 확정했다.
	- 채택: §1 표기(em dash 금지, 인용부호 구분, 하위 불릿 탭 들여쓰기).
	- 채택: §3 사유 서술(이유는 삭제하지 않되 장황한 수식어는 압축).
	- 채택: §7 섹션 구성(`##`/`###` 넘버링, 섹션 앞 구분선).
	- 미채택: §2 중복 방지(같은 주제를 여러 섹션에 걸쳐 재논의·정정하는 게 이 문서의 의도된 구조).
	- 미채택: §4 히스토리 vs 스펙 분리(GDD 등에서 히스토리를 이 문서로 보내기 위한 규칙이라 자기 자신에 재귀 적용 불가).
	- 미채택: §5 편집 절차(섹션마다 이미 날짜가 있어 중복).
	- 미채택: §9 문서 간 독립성(`GDD.md` 전용 규칙).

3. **불릿은 '결정 단위'로 묶는다.**
	- 볼드 리드 + 콜론 형태(`- **주제**: 근거.`)를 기본으로 한다.
	- 하위 불릿을 쓸 땐 상위 불릿엔 결정(무엇)만 남기고, 그 근거·세부사항(왜/어떻게)은 하위 불릿으로 내린다.
		- 한 불릿에 결정과 근거를 같이 욱여넣지 않는다.
	- 한 불릿 안에 문장이 여러 개 나열돼 있으면 문장 단위로 전부 하위 불릿으로 쪼갠다(2026-08-22 갱신: 기존 '이유·인과 서술은 예외' 조항 삭제).
		- 상위 불릿은 표제(볼드 리드가 있으면 그것) + 첫 문장만 남긴다.
		- 두 번째 문장부터는 이유·인과 서술이든 병렬적 사실이든 예외 없이 각각 독립된 하위 불릿 한 줄로 내린다.
		- 파일명/버전/섹션 번호 표기에 쓰인 마침표나 인용·괄호 안쪽의 마침표는 문장 경계로 보지 않는다.
	- 순서 자체가 내용인 논의 요약은 번호 매긴 문단으로 남겨도 된다.
	- 사유는 삭제하지 않는다.
	- 압축은 하되(§3), 정보값 없는 수식어만 걷어낸다.
	- 본문 도입부는 완결된 문장으로 쓴다.
		- 명사구와 콜론만 있는 레이블형 문장('~ 분리:')은 쓰지 않는다.
	- 서술 흐름과 무관하게 최종 확정된 목록이나 결론을 요약하는 문장은 블록쿼트로 분리한다.
	- 문장 종결은 '~였다'/'~했다'/'~없다'처럼 완결된 어미로 쓴다.
		- 꼭 필요한 경우가 아니면 '~였음'/'~없음'/'~함' 같은 명사형 종결은 쓰지 않는다.

4. **파일 번호와 소속 챕터 번호는 기록 묶음의 등장 순서를 따른다.**
	- 파일명은 `NN-Topic.md` 형식을 사용하고, 파일 번호와 내부 `## N` 번호를 맞춘다.
	- 번호는 정렬과 참조를 위한 기록 묶음 번호이며 `DevPlan.md`의 스테이지 번호가 아니다.
	- 새 결정 하나마다 파일을 만들지 않는다. 기존 파일의 범위를 벗어나는 큰 작업 축이 생겼을 때 다음 번호의 파일을 만든다.
5. **사용자 결정이 끝났거나 구현이 완료된 사항만 기재한다.**
	- 아직 사용자 결정을 받지 않은 설계 제안, 착수 전 계획은 이 문서에 기재하지 않는다.
		- 그런 내용은 `DiscussionDraft.md`(또는 대화 자체)에 먼저 정리해 사용자 검토·결정을 받고, 확정된 결과만 이 폴더로 옮긴다.
	- 이유: 이 문서는 '그 당시엔 이렇게 판단/논의했다'는 경위를 보존하는 문서(위 2번)이지, 결정 전 초안이나 미착수 계획을 보관하는 곳이 아니다.
		- 미확정 내용이 섞이면 이 문서를 신뢰 가능한 확정 스냅샷으로 읽을 수 없게 된다.
6. **편집 전에 이 파일과 대상 기록 파일을 함께 읽는다.**
	- 각 기록 파일 상단은 이 파일을 공통 작성 규칙으로 가리킨다.
	- 프로젝트 작업 지침도 개발 노트 편집 전에 이 파일을 읽도록 유지한다.
7. **결정 변경 시 영향을 받는 이전 기록에 최신 위치를 안내한다.**
	- 사용자 확정일: 2026-10-15.
	- 새 결정 기록을 작성할 때 이번 변경과 관련된 기존 결정·코드 안내·적용 절차·검증 기록을 확인한다.
	- 영향을 받는 절의 제목 아래 메타데이터 영역에 `> 후속 변경(안내 작성일): [일부 변경] 변경된 부분과 최신 기록 링크.` 형식으로 안내한다.
	- 절 전체가 대체되면 `[대체됨]`, 판단 전체가 폐기되면 `[폐기됨]`으로 표시한다.
	- 일부 변경은 바뀐 부분을 명시하고, 유효한 다른 내용까지 폐기된 것으로 표시하지 않는다.
	- 과거 검증은 당시 구현에 대한 결과로 보존하며, 변경 후 동작의 재검증 완료로 해석하지 않도록 안내한다.
	- 후속 변경이 다시 생기면 관련 안내 링크를 현재 결론으로 갱신한다.
	- 당시 설명·사유·검증 결과와 제목·앵커는 유지한다.
	- 전체 문서를 매번 재정리하지 않고 이번 변경의 영향 범위만 확인한다.
