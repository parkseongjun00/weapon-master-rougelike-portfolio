## 2. 메타 시스템

### 2.1 칭호·도감 중심의 메타 진행

<a id="21-착수-전-메타-진행-재설계-논의-요약"></a>

> 일자: 2026-07-30

- **문제**

	- 무기 해금·코스메틱·메타 화폐 중심의 진행이 파워 무관 원칙과 1인 개발 범위에 맞는지 재검토했다.

- **결정**

	| 항목 | 결정 |
	|---|---|
	| 영구 전투력 성장 | 제외 |
	| 무기 종류·등급 해금 | 제외, 처음부터 필드에서 조우 가능 |
	| 코스메틱 | 당시 아트 제작 비용을 고려해 칭호로 대체 |
	| 메타 화폐 | 용처를 억지로 만들지 않고 제외 |
	| 메타 진행 | 조건 달성 칭호·발견 기반 도감 |
	| 콘텐츠 규모 | 시스템과 최소 데이터부터 구현 |

- **근거**

	- 영구 파워 상승은 같은 적·환경에서 즉흥 판단의 비중을 낮출 수 있다고 판단했다.
	- 해금해도 실제 획득이 확률에 달리면 해금과 결과가 직접 연결되지 않는다.
	- 화폐를 쓸 대상이 사라졌으므로 화폐 자체도 제거했다.
	- 난이도 해금은 대안으로 검토했지만 채택하지 않았다.

- **검증과 한계**

	- 사용자 설계 결정이다. 장기 동기나 플레이 효과를 실측한 결과는 아니다. 당시 검토한 대안과 실제 채택한 개발 범위는 구분한다.

### 2.2 저장 접근의 단일 창구

<a id="22-savesystem-단일-창구-원칙"></a>

<a id="23-savesystem-구현-세부사항"></a>

> 일자: 단일 창구 2026-07-30, API·저장 정책 2026-07-31

- **문제**

	- 칭호·도감 저장이 늘어날 때 PlayerPrefs 호출과 저장 신뢰성 대응이 여러 곳에 흩어질 수 있었다.

- **결정**

	- 세이브는 단일 SaveSystem 창구를 통해 읽고 쓰도록 했다.

	| 주제 | 결정(2026-07-31) |
	|---|---|
	| API | PlayerPrefs의 int·float·string을 그대로 감싼다. |
	| 저장 시점 | Set 호출마다 PlayerPrefs.Save를 수행한다. |
	| 키 소유권 | 각 호출부가 자신의 저장 키를 소유한다. |
	| bool API | 실제 사용처가 없어 추가하지 않는다. |

- **근거**

	- 대상 빌드의 비동기 저장·동기화 위험에 대응할 위치를 한 곳에 모아, 저장 방식 변경 때 호출부를 함께 수정하지 않도록 했다.
	- 낮은 저장 빈도에서는 자동 flush가 호출 누락 위험을 줄이는 데 유리했다.
	- 창구는 키 레지스트리가 아니라 저장 통로로 한정하고, 필요하지 않은 타입 변환 규칙은 미리 만들지 않았다.

- **검증과 한계**

	- 대상 빌드 저장 유실을 이 프로젝트에서 재현한 결과가 아니라 위험을 고려한 설계다.
	- 2026-07-31에 런 기록의 직접 PlayerPrefs 호출을 창구 경유로 바꾸고 기존 키는 유지했다. 실제 대상 빌드 저장 신뢰성 검증 결과는 없다.
	- SaveHandler로의 이름 변경은 2.8에 보존한다.

### 2.4 무기별 고정 등급과 스탯 설정

<a id="24-등급rarity-시스템-최종-확정"></a>

> 일자: 2026-07-31

- **문제**

	- 등급을 스폰마다 무작위로 바꾸는 구현과 무기 고유 등급이라는 의도가 어긋났다.

- **결정**

	- 등급은 무기 정의에 고정하고 일반·희귀·영웅·전설 네 단계로 둔다.
	- 공격력·쿨다운·최대 내구도는 등급을 반영한 최종값으로 직접 저작한다.
	- 사거리·투사체 속도는 무기 정체성 값으로 유지한다.
	- 당시 등급 틴트는 프리팹 제작 시 굽고 스포너의 재계산을 제거했다.

- **근거**

	- 무기 고정 등급과 개체별 편차를 분리했다.
	- 런타임의 총 예산·카테고리 비중 공식보다 무기별 역할에 맞는 직접 입력을 택했다.
	- 고정 등급의 틴트를 스폰 때마다 다시 계산할 필요가 없었다.

- **검증과 한계**

	- 당시 무기 두 종은 모두 일반 등급이었다. 등급별 수치 예산과 색은 밸런스 확정값이 아니었다. 제작 뒤 등급을 바꾸면 구운 재질 색이 자동 갱신되지 않는 한계를 감수했다. 이후 데이터 저작 구조는 [3.17](03-PlayerAnimation.md#317-프리팹-중심-무기-데이터와-스폰-등록-통합)로 바뀌었다.

### 2.5 무기 컨디션의 공격력 편차

<a id="25-컨디션condition-최종-확정"></a>

> 일자: 2026-07-31

- **문제**

	- 무기 고유 등급을 유지하면서 같은 무기의 스폰 개체별 작은 편차를 표현하고자 했다.

- **결정**

	| 주제 | 결정 |
	|---|---|
	| 영향 | 공격력만 변경 |
	| 값 | 매우 나쁨 -10%, 나쁨 -5%, 보통 0%, 좋음 +5%, 매우 좋음 +10% |
	| 분포·시점 | 균등 분포, WeaponBase.Awake에서 결정 |
	| 제외 | 맨손 정의의 hasCondition=false |
	| 소유 | 별도 컴포넌트 없이 WeaponBase의 상태로 관리 |

- **근거**

	- 내구도 편차는 무기 수명을 지나치게 좌우하고 공격속도 편차는 상태·품질 개념과 맞지 않는다는 사용자 판단이었다.
	- 스포너는 생성 대상·시점·위치만 알도록 했다.
	- 명시적 특성 필드가 Pickup 존재 여부로 추론하는 방식보다 의도를 잘 드러냈다.

- **검증과 한계**

	- 수치·분포는 시험용이며 불공평하면 폐지하기로 조건부 확정했다.
	- 칭호의 전설 획득 조건은 VeryGood 획득으로 바꿨다.
	- 도감 축 문제의 결론은 2.13, 컨디션 계산 정리는 [3.12](03-PlayerAnimation.md#312-근접-히트-판정-animation-event-이관--공격속도-재생속도-동기화-구현-완료)에 기록했다.

### 2.8 클래스 접미사의 역할별 구분

<a id="28-네이밍-컨벤션-4분류로-재정의"></a>

<a id="221-savesystem--savehandler-weaponcollectionsystem--weaponcollectionhandler-개명"></a>

<a id="27-네이밍-컨벤션-system--manager"></a>

> 일자: 초기 기준 2026-08-01, 재정의 2026-08-02, 적용 범위·개명 2026-08-04

- **문제**

	- static 접근 가능성과 씬 컴포넌트 존재 여부가 하나의 분류에 섞여 모호했다.
	- 2026-08-01에는 static 접근을 System, 씬 단일 객체를 Manager로 구분했으나 서로 다른 축이 섞여 다음 날 아래 기준으로 대체했다.

- **결정**

	| 접미사 | static 접근 | 씬 컴포넌트 | 개수 |
	|---|---|---|---|
	| System | 가능 | 존재 | 제한 없음 |
	| Handler | 가능 | 없음 | 해당 없음 |
	| Manager | 불가 | 존재 | 단일 |
	| Controller | 불가 | 존재 | 복수 가능 |

	- Data·Definition·Pool 등 더 정확한 역할명이 있으면 우선한다. 기존 이름의 소급 변경은 개별 리팩터링에서 명시적으로 정한 범위에 한정했다.
	- 2026-08-04에는 씬 객체가 없는 static 유틸리티인 SaveSystem·WeaponCollectionSystem을 SaveHandler·WeaponCollectionHandler로 개명하고 static을 유지했다.

- **근거**

	- 서로 다른 두 축을 분리해 이름과 실제 접근 구조의 불일치를 줄였다.
	- 무상태 저장 통로의 static과 씬 참조 제약을 우회하는 MonoBehaviour의 Instance 접근은 구분했다.

- **검증과 한계**

	- 표는 8월 2일 확정 당시 문서화만 했고 후속 구현에서 적용했다. 8월 4일의 저장·도감 개명에는 별도 실행 검증 기록이 없다. AchievementSystem은 당시 유지했고 이후 2.24에서 개명했다.

### 2.11 칭호 정의와 조건 판정의 분리

<a id="211-칭호-so-기반-구현으로-재설계"></a>

<a id="210-칭호-최소-세트"></a>

> 일자: 최소 조건 2026-07-30, SO 재설계 2026-08-01

- **문제**

	- 칭호마다 enum과 판정 분기를 추가하는 구조를 줄이면서 단일 런·누적·연속 시간 조건을 구분해야 했다.

- **결정**

	- 칭호별 AchievementDefinition SO와 로스터를 만들고 metric·threshold로 판정했다.
	- 저장 키는 정의 에셋 이름을 사용했다.
	- 당시 Tracker는 게임 이벤트 구독·측정·판정, static System은 저장·측정값 전달을 맡았다.

	| 당시 칭호 | 측정값 | 조건·범위 |
	|---|---|---|
	| 첫 무기 획득 | WeaponEquipCount | 평생 1회 |
	| 첫 처치 | EnemyKillCount | 평생 1회 |
	| 생존자 | SurvivalSeconds | 단일 런 300초 |
	| 학살자 | EnemyKillCount | 누적 100회 |
	| 명품 | WeaponConditionTier | VeryGood(4) 최초 획득 |
	| 소모품 | WeaponDestroyedCount | 누적 10회 |
	| 맨몸 파이터 | UnarmedSeconds | 단일 런 내 연속 60초 |
	| 단골 | RunPlayedCount | 누적 10판 |

	- 생존·맨손 시간은 구간 종료 이벤트에서 측정하고 매 프레임 폴링하지 않았다.
	- 무기 파괴·수동 드롭의 공통 상태 정리 지점에서 맨손 전환을 알리도록 했다.
	- 맨손 시작 시각은 nullable 값 하나로 상태와 시각을 함께 표현했다.

- **근거**

	- 칭호 수가 늘어도 측정 종류는 작게 유지하려고 데이터와 판정을 분리했다.
	- 전설 획득은 잘못된 랜덤 등급 전제였으므로 VeryGood 조건으로 교체했다.
	- 누적·단일 런 구분은 카운터 수명과 저장 위치를 결정한다.
	- 해금 완료 metric의 추적 중단 최적화는 낮은 비용에 비해 새 질의가 필요해 제외했다.

- **검증과 한계**

	- 코드 구현 후 사용자 결정으로 8개 조건의 Play 검증은 생략했다. 구간 종료 판정이므로 생존 중 즉시 해금하는 방식과는 구분한다. 책임 재분배는 2.12, static 제거는 2.24에 기록했다.

### 2.12 칭호 측정값 전달과 판정의 단방향 연결

<a id="212-칭호-achievementsystemachievementtracker-책임-재분배"></a>

> 일자: 2026-08-02

- **문제**

	- Tracker가 System에 보고하면 이벤트가 다시 같은 Tracker를 불러 판정하는 왕복 구조였다.

- **결정**

	| 구성 | 변경 후 책임 |
	|---|---|
	| AchievementTracker | 게임 이벤트를 측정값으로 번역 |
	| AchievementSystem | 로스터·저장·threshold 판정 |

	- OnMetricReported를 제거하고 Tracker → System 단방향으로 바꿨다.
	- UpdateMetric은 역대 최고값을 저장한 뒤 갱신된 값만 판정했다.
	- 당시 System은 로스터를 갖는 MonoBehaviour와 static API를 함께 사용했다.

- **근거**

	- 호출자와 구독자가 같은 불필요한 왕복을 줄이고, 향후 진행도 표시에 필요한 순간값의 최고 기록을 보존했다. 해금 UI가 없으므로 알림 이벤트는 만들지 않았다.

- **검증과 한계**

	- 코드를 반영했으나 당시 Unity 컴파일·Play 검증은 미실행이었다. static을 유지한 편의상 근거는 이후 2.24에서 재검토해 제거했다.

### 2.13 무기 정의별 도감 슬롯 구성

<a id="213-무기-도감-최소-구조"></a>

> 일자: 최초 설계 2026-07-30, 재확정 2026-08-01

- **문제**

	- 무기 종류 × 등급 도감은 등급을 랜덤 스폰으로 오해한 전제에 의존했다.

- **결정**

	- 고유 WeaponDefinition 하나당 슬롯 하나로 확정했다.
	- 컨디션은 도감 분류에서 제외하고 실제 획득 시 발견을 기록했다.
	- 당시 맨손은 startsDiscovered로 처음부터 발견된 상태로 표시했다.
	- 로스터를 읽어 슬롯을 구성하고 별도 조합표는 만들지 않았다.

- **근거**

	- 등급은 무기에 고정되고 컨디션은 런 한정 상태이므로 영구 도감의 별도 축으로 맞지 않았다.
	- 맨손은 Equip 경로를 거치지 않아 일반 발견 저장으로 처리할 수 없었다.
	- 저장 창구가 맨손 예외를 알지 않도록 정의 데이터로 표현했다.

- **검증과 한계**

	- 당시 맨손 포함 세 슬롯으로 확정했다.
	- 예외 필드 구조와 도감 등급 축은 당시 검토 후보였으며 후속 구현의 확정 사항은 아니다.
	- 이후 맨손의 필드 로스터 제외와 SO 제거는 [3.17](03-PlayerAnimation.md#317-프리팹-중심-무기-데이터와-스폰-등록-통합)에 기록했다.

### 2.14 칭호·도감 화면 보류와 디버그 UI

<a id="214-칭호도감-뷰화면-배치-3단계는-로직저장까지만"></a>

> 일자: 2026-07-30

- **문제**

	- 칭호·도감의 정식 메뉴 진입점이 없는데 임시 플레이어 화면을 만들면 이후 다시 통합해야 했다.

- **결정**

	- 정식 뷰는 미루고 조건 판정·저장을 먼저 구현했다. 개발 검증용으로만 에디터·디버그 빌드에서 OnGUI 오버레이와 카운터 조절 버튼을 두기로 했다.

- **근거**

	- 플레이어용 임시 UI의 이중 작업을 피하되 누적 조건을 반복 플레이 없이 확인할 수 있어야 했다.

- **검증과 한계**

	- 당시 구현 순서의 결정이다. 디버그 오버레이는 정식 메뉴의 기반으로 채택한 것이 아니며 이 절에 사용자 화면 검증 결과는 없다.

### 2.16 증강 배율의 조회 방식에서 전달 방식으로 전환

<a id="216-증강-배율-적용-구조-개편"></a>

<a id="29-씬-전용-오브젝트는-직렬화-필드-대신-static-instance-접근"></a>

<a id="215-이후-단계-재검토-후보"></a>

<a id="217-playeraugmentsystem_augmentinstancesbystat-정리"></a>

> 일자: 2026-08-03

- **문제**

	- 무기·이동·체력이 PlayerAugmentSystem을 직접 조회해 부가 시스템을 알아야 했다.
	- 당시 프리팹 에셋에는 씬 객체 참조를 직렬화할 수 없어 씬 단일 객체의 Instance를 Awake에서 등록하고 OnDestroy에서 해제하는 접근을 사용했다(2026-08-03). 이 제약을 유지하면서 직접 조회 의존을 제거해야 했다.

- **결정**

	| 대상 | 변경 |
	|---|---|
	| 체력·이동 | 내부 배율을 보관하고 명시적 메서드로 갱신 |
	| WeaponSlot | 공격력·공격속도 배율을 보관 |
	| 무기 | TryAttack 인자로 배율을 받아 최종값 계산 |
	| 증강 | LevelUp에서 대상에게 새 배율 전달 |

	- 배율 기본값은 1이며 공격속도 배율은 쿨다운에 나눗셈으로 적용했다.
	- HealthBarUI.OnEnable → HealthComponent.MaxHealth에서 초기화 순서 문제가 발생했던 근거를 보존하기 위해, 배열 선택과 필드 초기화 시점의 주석을 유지했다(2026-08-03).

- **근거**

	- 무기 교체와 무관하게 고정된 슬롯이 배율을 소유하면 교체마다 재주입할 필요가 없다.
	- 무기가 자기 컨테이너를 역참조하지 않게 했다.
	- 트리거가 자기 LevelUp 하나여서 별도 중계 클래스를 만들지 않았다.
	- 단일 구현체를 인터페이스로 감싸기보다 핵심 시스템의 증강 의존을 제거하는 방식을 택했다(2026-07-30~08-03의 검토).
	- 소비 경로가 줄었다는 사실만으로 이전 초기화 문제의 재발 방지 근거를 제거하지 않았다.

- **검증과 한계**

	- 코드를 반영하고 증강 타입을 아는 파일이 다섯 개에서 두 개로 줄었음을 확인했다. 당시 Unity 컴파일·Play는 미확인이었다.
	- 초기화 주석 보존에는 별도 실행 검증 기록이 없다. 고정 배열·사전 채우기는 이후 2.19에서 제거했으므로 당시 전제와 구분한다.
	- 식별 구조는 2.19, 공통 무기 슬롯은 [3.31](03-PlayerAnimation.md#331-범용-무기와-사람형-모션-통합)에 후속 기록을 남겼다. 다른 씬 참조 경로의 후속 변경은 2.20·2.23·2.24를 따른다.

### 2.18 공격속도와 쿨다운의 단위 변환

<a id="218-공격속도-gdd-정의초당-공격-횟수와-내부-표현쿨다운-초이-다른-이유"></a>

> 일자: 2026-08-03

- **문제**

	- GDD의 공격속도는 초당 횟수인데 코드는 다음 공격까지의 초 단위 쿨다운을 저장했다.

- **결정**

	| 용도 | 표현 |
	|---|---|
	| 내부 저장 | cooldown(초) |
	| 증강 적용 | EffectiveCooldown = Cooldown / attackSpeedMultiplier |
	| 공격속도 UI | 1 / cooldown(초당 횟수) |

- **근거**

	- 시간과 횟수는 역수 관계다. 다음 공격 시각을 비교하는 루프에는 초가 자연스럽고, 배율로 나눠야 GDD의 초당 횟수 배율과 정확히 일치한다.

- **검증과 한계**

	- 사용자가 내부 표현을 확인했다. cooldown 1.34는 초당 1.34회가 아니라 약 0.746회다. 당시 수치 UI는 없었으며 표시할 때 단위 변환을 누락하지 않아야 한다.

### 2.19 증강 식별과 효과 적용의 분리

<a id="219-증강-시스템-식별-키를-stattype에서-augmentdefinition으로-전환--카테고리-기반-효과-적용"></a>

> 일자: 2026-08-03

- **문제**

	- StatType이 증강 식별과 효과 적용 대상을 동시에 나타내 무기 특화 증강을 수용하지 못했다.

- **결정**

	| 책임 | 변경 |
	|---|---|
	| 증강 식별 | AugmentDefinition 키의 Dictionary, 선택 시 인스턴스 생성 |
	| 효과 적용 | AugmentCategory enum과 switch |
	| 같은 스탯의 복수 증강 | 배율을 곱해 합산 후 전달 |
	| 전체 카탈로그 | AugmentSelectionManager |
	| 플레이어 상태 | PlayerAugmentManager |
	| 팝업 데이터 | 표시용 AugmentPopupOption |
	| 레벨업 완전 회복 | 독립 LevelUpFullHeal의 이벤트 구독 |

- **근거**

	- 식별 키와 효과 분기를 분리해 스탯 하나당 증강 하나라는 결합을 풀었다.
	- 현재 효과는 세터 선택 수준이라 상속 전략보다 enum 분기가 단순했다.
	- 선택 UI는 상태를 캐싱하지 않고 관리자에게 조회하므로 상태 원본은 하나다.
	- 완전 회복은 팝업과 별개 반응이며 공용 HealthComponent가 PlayerXP를 알지 않도록 했다.

- **검증과 한계**

	- 코드를 반영했다. 이 절에 실행 검증 결과는 없다. 카테고리가 3~4개를 넘거나 전용 필드가 쌓이면 상속을 검토한다는 당시 기준을 남겼다. 단순한 미래 확장이 아니라 이미 예정된 무기 특화 요구가 구조 변경의 근거였다.

### 2.20 런 기록의 이벤트 수신과 static 접근 제거

<a id="220-runstats--runrecordmanagerrunstatsui--runrecordui-개명--static-instance-제거"></a>

> 일자: 2026-08-04

- **문제**

	- RunStats가 능동적인 런 기록·저장을 수행하고, static 접근도 실제 호출 경로와 맞는지 재검토가 필요했다.

- **결정**

	- RunRecordManager·RunRecordUI로 개명했다.
	- 스포너의 OnEnemyKilled를 구독하고 씬 소비자는 직렬화 참조로 연결했다.
	- static Instance와 외부 AddKill 호출을 제거했다.
	- 다른 클래스 이름만 빌려 설명하는 주석은 줄이고 자체 설계 근거는 유지했다.

- **근거**

	- Stat은 전투 StatType과 의미가 겹쳤다.
	- 씬 소비자는 직렬화 참조가 가능해 편의성만을 위한 static이 필요하지 않았다.
	- 처치 통보를 스포너의 경계에 모으면 적 프리팹이 기록 관리자를 알 필요가 없다.

- **검증과 한계**

	- 코드·씬 빌더 연결을 변경했다. 별도 실행 검증 결과는 이 절에 없다. 풀 반납과 처치 통보의 이후 분리는 [5.2](05-EnemyAnimation.md#52-전투-처리와-표현의-연결), 스포너 접근 변경은 2.23을 따른다.

### 2.22 로스터 에디터의 공통 재스캔 로직 통합

<a id="222-로스터-에디터-3종을-제네릭-베이스로-통합"></a>

> 일자: 2026-08-04

- **문제**

	- 세 로스터 Inspector의 재스캔 로직이 타입·폴더·필드명만 다르고 중복됐다.

- **결정**

	- `RosterEditor<TRoster,TDefinition>`에 공통 로직을 모으고 구체 Editor는 폴더·필드명과 CustomEditor 속성을 소유하도록 했다.

- **근거**

	- 미래 로스터 증가 예상이 아니라 이미 존재하는 세 중복이 근거였다. 공통 버그를 한 곳에서 수정할 수 있게 했다.

- **검증과 한계**

	- 코드는 약 160줄에서 베이스 57줄과 구체 클래스당 약 13줄로 줄었다. CustomEditor는 제네릭 베이스가 아닌 구체 클래스에 붙여야 했고, System.Object와 충돌하지 않도록 UnityEngine.Object를 명시했다. 별도 실행 검증 결과는 없다.

### 2.23 적 처치의 보상·기록·풀 반납 책임 분리

<a id="223-enemyxprewardenemyaiachievementtracker-적-처치-반응-재분배--enemyspawner-static-instance-제거"></a>

> 일자: 2026-08-04

- **문제**

	- EnemyXPReward가 XP·칭호·풀 반납을 함께 처리했고 적 프리팹의 스포너 접근을 static으로 연결했다.

- **결정**

	| 구성 | 당시 책임 |
	|---|---|
	| EnemyXPReward | XP 지급 |
	| EnemyAI | 사망·풀 반납 |
	| AchievementTracker | 처치 이벤트를 업적 카운터로 변환 |
	| EnemySpawner | 생성 시 SetSpawner 주입, static Instance 제거 |

- **근거**

	- 이벤트 반응을 관심사별로 분리했다. 당시 스포너가 매번 사망 이벤트를 구독하는 대안은 풀 재사용 때 구독 누적을 막는 처리가 추가로 필요해 제외했다. HealthComponent에 적 풀링 전용 정리를 넣는 것도 피했다.
	- 적 프리팹에 씬의 스포너 참조를 직렬화할 수 없는 제약은 생성 시 SetSpawner로 전달해 해결했다.

- **검증과 한계**

	- 구독 누적과 해제 대안의 실행 순서를 검토했다. 이 절에 실제 Play 검증 결과는 없다. 이후 [5.14](05-EnemyAnimation.md#514-적에서-스포너-참조-제거)는 대여 목록과 명시적 구독 해제를 도입해 이벤트 방식을 채택했다. 당시 대안 기각을 이벤트 방식 자체의 영구 금지로 읽지 않는다.

### 2.24 칭호 관리자의 static 접근 제거

<a id="224-achievementsystem--achievementmanager-개명--static-전면-제거"></a>

> 일자: 2026-08-04

- **문제**

	- 업적의 실제 소비자가 씬 객체 두 곳뿐인데 편의상 static Instance를 사용했다.

- **결정**
