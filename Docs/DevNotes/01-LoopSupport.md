## 1. 코어 루프 지원

### 1.1 증강 정의·선택·효과 적용의 책임 분리

<a id="11-증강-효과-적용-구조"></a>

> 일자: 2026-07-27

- **문제**
	- 증강 정의·플레이어별 레벨·선택 UI·실제 스탯 적용의 책임을 분리해야 했다.

- **결정**

	| 구성 | 당시 책임 |
	|---|---|
	| AugmentDefinition | 대상 StatType·최대 레벨·레벨별 최종 보너스 |
	| AugmentInstance | 현재 레벨·상한·현재 보너스 계산 |
	| PlayerAugments | StatType 인덱스 배열로 플레이어 레벨 관리 |
	| PlayerXP | XP·레벨 임계값 판정과 OnLevelUp 발행 |
	| AugmentSelectionController | 후보 선택·일시정지·연속 레벨업 큐 |
	| 무기·이동·체력 | 필요한 증강 배율 조회·적용 |

	- 레벨별 보너스는 누적합이 아니라 해당 레벨의 최종값으로 저장했다.
	- v1 증강은 공격력·공격속도·이동속도·최대체력으로 한정했다.
	- 후보가 없으면 선택창 없이 완전 회복하고, 연속 레벨업은 마지막 선택까지 일시정지를 유지했다.
	- 일시정지 중 UI 연출에는 unscaledDeltaTime을 사용했다.

- **근거**

	- 고정된 소수 StatType에는 배열이 단순하다고 판단했다.
	- 맨손도 MeleeWeapon이므로 별도 증강 경로를 만들지 않았다.

- **검증과 한계**

	- 설계 확정 기록이며 이 절에 실행 검증 결과는 없다. 카탈로그 분리는 1.2, 배율 전달은 [2.16](02-MetaSystems.md#216-증강-배율-적용-구조-개편), 식별 키 전환은 [2.19](02-MetaSystems.md#219-증강-시스템-식별-키를-stattype에서-augmentdefinition으로-전환--카테고리-기반-효과-적용)에 후속 기록을 남겼다.

### 1.2 증강 카탈로그와 플레이어 상태 분리

<a id="12-증강-카탈로그를-augmentroster로-분리"></a>

> 일자: 2026-08-03

- **문제**

	- PlayerAugments가 게임 전체 증강 카탈로그와 플레이어가 선택한 레벨을 함께 소유했다.

- **결정**

	| 데이터 | 분리 후 소유자 |
	|---|---|
	| 모든 증강 정의 | AugmentRoster SO |
	| 플레이어별 증강 인스턴스·레벨 | PlayerAugments |

	- 로스터는 정의 목록·등록·에디터 재스캔만 담당하도록 했다.

- **근거**

	- 전역 카탈로그와 플레이어 상태는 수명과 책임이 다르므로 분리했다.

- **검증과 한계**

	- 코드와 씬 빌더 배선을 변경했다. 이 절에 별도 실행 검증 결과는 없다. 로스터의 후속 소유권 변경은 [2.19](02-MetaSystems.md#219-증강-시스템-식별-키를-stattype에서-augmentdefinition으로-전환--카테고리-기반-효과-적용)를 따른다.

### 1.4 런 결과 저장 방식

> 일자: 2026-07-27

- **문제**

	- 사망 후 마지막 런의 생존시간·처치수를 보존할 최소 저장 방식이 필요했다.

- **결정**

	- PlayerPrefs의 float·int 값 두 개로 저장하고 결과 화면은 별도로 구현하기로 했다.

- **근거**

	- 원시 값 두 개에 JSON 직렬화는 불필요하다고 판단했다.
	- 대상 빌드 저장을 고려해 PlayerPrefs를 백엔드로 선택하고 파일 I/O 방식은 배제했다.
	- 구조화된 데이터가 실제로 늘어날 때 직렬화를 검토하기로 했다.

- **검증과 한계**

	- 저장 방식의 선택이며 대상 빌드 저장 신뢰성 실측 결과는 아니다. 저장 창구와 정책은 [2.2](02-MetaSystems.md#22-저장-접근의-단일-창구)에 기록했다.

### 1.5 무기 수치와 프리팹 생성 코드 분리

<a id="15-무기-scriptableobject-리팩터링-범위"></a>

> 일자: 2026-07-27

- **문제**

	- 무기 수치가 프리팹 제작 코드에 직접 들어 있어 정의 데이터를 분리할 필요가 있었다.

- **결정**

	- 무기 수치를 WeaponDefinition SO로 옮기고 맨손도 같은 정의 경로를 사용하기로 했다.
	- 이미 채택된 이동속도 페널티·등급 필드는 값의 사용 시점보다 먼저 정의했다.
	- 당시에는 빌더가 산출물을 재생성하므로 기존 무기 프리팹의 별도 이전 절차를 두지 않았다.

- **근거**

	- 확정된 필드를 뒤늦게 추가하는 재작업과 맨손만 별도 데이터 경로를 갖는 중복을 줄이기 위한 선택이었다.

- **검증과 한계**

	- 당시 리팩터링 범위의 확정 기록이다. 이후 SO에서 프리팹 내장 데이터로 바꾼 이유와 저장 키 호환은 [3.17](03-PlayerAnimation.md#317-프리팹-중심-무기-데이터와-스폰-등록-통합)에 기록했다.

### 1.6 적 체력바·피해 숫자의 Canvas 없는 표시

<a id="16-적-체력바데미지-숫자-렌더링-방식"></a>

<a id="19-2단계-ui-라운드-완료-보고에서-승격"></a>

> 일자: 2026-07-28

- **문제**

	- 다수 적의 체력바·데미지 표시를 대상 빌드을 고려한 낮은 비용의 구조로 구현해야 했다.

- **결정**

	| 표시 | 선택 |
	|---|---|
	| 체력바 | SpriteRenderer 두 장, 채움의 localScale.x 조절 |
	| 데미지 숫자 | Canvas 없는 3D TextMeshPro |
	| 피해량 통지 | HealthComponent.OnDamaged(amount) |
	| 체력바 채움(2026-07-30) | 중앙 피벗 스프라이트의 축소 시 localPosition.x를 보정해 왼쪽 기준 유지 |
	| 스프라이트(2026-07-30) | 한 번 생성·저장한 에셋 재사용 |
	| 피해 표시 의존 방향(2026-07-30) | DamagePopupSpawner를 UI 폴더·네임스페이스에 두고 플레이어·적 양쪽에 부착 |

	- 개체별 World Space Canvas와 통합 오버레이 좌표 투사 방식을 제외했다.

- **근거**

	- 적 수 증가에 따른 Canvas 비용과 GC·드로우콜 여유를 고려했다.
	- 오버레이 방식은 좌표 추적·풀링 관리가 더 필요해 현재 요구에 비해 복잡했다.
	- 기존 OnHealthChanged만으로는 실제 피해량을 전달할 수 없었다.
	- 2026-07-30에는 별도 피벗 스프라이트 없이 체력바 채움의 왼쪽 기준을 유지했다.
	- DamagePopupSpawner는 UI 풀을 참조하므로 Core가 UI에 의존하지 않도록 UI에 배치했다.

- **검증과 한계**

	- 당시에는 고정 카메라를 이유로 회전 보정이 불필요하다고 판단했으나 부모 회전을 놓쳤다. 실제 플레이에서 확인한 정정은 1.8을 따른다. 이 선택 자체의 대상 빌드 성능 비교는 기록하지 않았다.
	- 2026-07-30의 채움·재사용·의존 방향 결정에는 별도 실행 검증 기록이 없다.

### 1.7 오브젝트 풀링 도입 범위

> 일자: 2026-07-28

- **문제**

	- 적·투사체·데미지 팝업의 반복 생성·파괴와 재사용 상태 초기화를 관리해야 했다.

- **결정**

	| 대상 | 당시 선택 |
	|---|---|
	| 적·투사체·데미지 팝업 | 오브젝트 풀 도입 |
	| 필드 무기 | 당시 저빈도 생성을 이유로 풀링 보류 |
	| 체력 | 체크아웃 때 명시적으로 초기화 |
	| 적 풀 소유권(2026-07-30) | EnemySpawner 내부 소유 |
	| 투사체 풀 소유권(2026-07-30) | ProjectilePool의 프리팹별 Dictionary |
	| 숫자 팝업 풀 소유권(2026-07-30) | 독립 DamageNumberPool |

- **근거**

	- 빈번한 Instantiate·Destroy에 따른 GC 압박을 줄이기 위한 선택이었다.
	- 재활성화 때 Awake가 다시 호출되지 않아 체력 초기화를 Awake에만 두면 이전 생애 값이 남는다.
	- 플레이어의 최초 생성 초기화는 유지해야 했다.
	- 2026-07-30에는 투사체 프리팹마다 재사용 대상을 구분하도록 풀 소유권을 정했다.

- **검증과 한계**

	- 도입 범위와 초기화 위험을 확정한 기록이다. 2026-07-30의 풀 소유권 결정에는 별도 실행 검증 기록이 없다. 당시 풀의 static 접근은 이후의 스포너 의존 제거 기록과 구분한다.

### 1.8 체력바·피해 숫자의 월드 회전 고정

<a id="18-적-체력바데미지-팝업-고정-회전-빌보드-불필요-판단-정정"></a>

> 일자: 2026-07-28

- **문제**

	- 카메라가 회전하지 않아도 적 루트가 회전하므로 자식 체력바의 localRotation만 고정하면 표시가 함께 돌아갔다.

- **결정**

	- FixedWorldRotation의 LateUpdate에서 체력바와 데미지 팝업의 월드 회전을 고정하고 같은 카메라 각도 상수를 공유했다.

- **근거**

	- 당시 카메라 각도는 상수여서 매 프레임 카메라 참조와 LookRotation을 계산하는 빌보드보다 단순한 월드 회전 고정으로 충분했다.

- **검증과 한계**

	- 실제 플레이에서 1.6의 회전 보정 불필요 판단이 틀렸음을 확인했다. 고정 시점 전제의 해결이며 카메라 회전이 달라지는 후속 구성까지 보장하지 않는다.
