## 3. 플레이어 캐릭터와 애니메이션

### 3.1 캐릭터 프리팹과 공통 애니메이션 구조

<a id="31-캐릭터-아키텍처-확정"></a>

<a id="32-애니메이션-클립-매핑-확정"></a>

> 일자: 2026-08-20

- **문제**

	- 신규 플레이어블 캐릭터 추가가 이미 결정돼 모델·애니메이션·충돌의 재사용 경계를 정해야 했다.

- **결정**

	| 대상 | 결정 |
	|---|---|
	| Rig | Humanoid 통일 |
	| CharacterDefinition | 표시명·캐릭터 프리팹·선택 Override Controller |
	| CharacterRoster | 캐릭터 정의 목록 |
	| 충돌 캡슐 | 캐릭터 프리팹이 소유 |
	| 모션 | 공용 Animator Controller와 캐릭터별 클립 매핑 |
	| 이동 | 코드 이동 유지, Root Motion 미사용 |
	- 초기 클립은 대기·속도 기반 이동·맨손 좌우 펀치·장착 근접 공격·원거리 사격 홀드에 배정했다(2026-08-20). 용도가 없는 Alert는 배정하지 않았다.

- **근거**

	- 스켈레톤 간 리타겟팅과 공용 상태 그래프를 활용하되, 캡슐 치수는 모델과 함께 보며 맞추도록 프리팹을 단일 원본으로 삼았다. 가상의 확장보다 이미 확정된 캐릭터 추가가 근거였다.
	- 사용자 합의로 정지 사격·스트레이프·후진 전용 클립 대신 기존 모션을 재사용했다. 반복 발사마다 클립을 재시작하지 않고 사격 자세를 유지했다(2026-08-20).

- **검증과 한계**

	- 설계를 확정하고 구현에 착수한 기록이다. Override Controller는 클립 매핑 용도이며 Humanoid가 아닌 리그나 다른 상태 그래프까지 해결하는 수단으로 해석하지 않는다. 공통 모션 전환은 3.31을 따른다.
	- 초기 배정은 사용자 설계 합의이며 별도 실행 검증 기록은 없다. 파일 교체는 3.4, 방향별 모션 검토는 3.5, 공통 모션 전환은 3.31을 따른다.

### 3.4 FBX 루트 불일치와 애니메이션 참조 복구

<a id="34-meshy-루트-노드-이름-불일치-해결--애니메이션-파일-교체"></a>

> 일자: 2026-08-22

- **문제**

	- Humanoid의 Copy From Other Avatar가 Hips 부모 불일치로 실패했다. 모델은 Armature, 클립은 서로 다른 루트 이름을 사용했다.

- **결정**

	| 시도 | 당시 결과 |
	|---|---|
	| AssetPostprocessor·meta 마커로 정규화 | 복잡도를 이유로 기각 |
	| Meshy With Skin 재다운로드 | 당시 루트 계층 일치로 채택 |
	| 파일명 정리 | 긴 접두·접미어만 제거하고 내부 Take 이름 유지 |
	| Controller GUID 텍스트 치환 | 실패 후 에디터에서 Motion 재연결 |

- **근거**

	- 모델과 같은 계층을 포함한 export가 별도 임포트 제어보다 단순하다고 판단했다. 파일 교체로 GUID가 바뀌어 기존 Controller 참조도 복구해야 했다.

- **검증과 한계**

	- fileID가 유지될 것이라는 가설은 실제 치환 실패로 폐기했다. 최종적으로 여섯 상태의 Motion을 수동 연결하고 Play 재생을 확인했다. With Skin에서도 재발한 후속 사례와 외부 정규화 도구는 3.9에 기록했다.

### 3.5 방향별 이동 모션 검토와 전진 클립 재사용

<a id="35-이동-방향과-조준애니메이션-방향-불일치-2d-blend-tree-검토-후-기각"></a>

> 일자: 2026-08-22

- **문제**

	- 몸이 조준 방향을 향하므로 뒤·옆 이동에서도 전진 클립이 재생됐다.

- **결정**

	| 대안 | 판단 |
	|---|---|
	| 몸 전체를 이동 방향으로 회전 | 자유 조준 때 상체 회전 문제가 생겨 기각 |
	| 전후·좌우 2D Blend Tree | 추가 클립 비용 대비 실익이 낮아 기각 |
	| 전진 클립 재사용 | 기존 단순화 유지 |

- **근거**

	- 사용자가 신규 클립 확보 비용보다 현재 단순화를 유지하는 쪽을 선택했다.

- **검증과 한계**

	- 버그 수정이 아니라 표현 범위의 확정이다. Mirror를 통한 좌우 재사용은 검증하지 않았다. 당시 폐기를 확정해 재검토 과제로 등록하지 않았다.

### 3.6 이동과 공격의 상하체 애니메이션 분리

<a id="36-상하체-애니메이션-분리-upper-body-레이어--avatar-mask-구현"></a>

> 일자: 2026-08-22

- **문제**

	- 이동 중 공격·사격을 재생하면 다리의 이동 표현까지 끊기는 문제를 분리해야 했다.

- **결정**

	- Base Layer는 이동, Upper Body는 상체 공격을 맡도록 Avatar Mask와 Override 레이어를 사용했다.
	- 공격하지 않을 때 Upper Body도 같은 LocomotionBlend를 참조했다.
	- 기존 Controller를 수정하는 별도 에디터 도구를 만들고 반복 실행을 고려했다.

- **근거**

	- 마스크로 다리를 제외해 공격 중에도 하체 이동을 유지했다.
	- Override의 기본 상태를 비우면 평소 팔이 고정되므로 같은 이동 블렌드를 재사용했다.
	- 구형 씬 빌더의 생성 가드는 기존 Controller를 갱신하지 못해 별도 적용 경로가 필요했다.

- **검증과 한계**

	- 최초에는 실행 대기였으나 사용자가 메뉴 적용 후 Play에서 상하체 동시 재생을 확인했다.
	- 후속 재생속도 설정은 3.12, 정지 전신·이동 하체의 공통 구조는 3.31로 변경했다.

### 3.9 Blender를 이용한 FBX 루트 이름 정규화

<a id="39-meshy-루트-노드-이름-불일치-재발-blender-헤드리스-정규화-도구-도입"></a>

> 일자: 2026-08-25

- **문제**

	- With Skin export로도 루트 이름 불일치가 재발해 입력 FBX를 정규화할 보완책이 필요했다.

- **결정**

	- Blender 헤드리스 재export로 명시적으로 선택한 FBX만 제자리 정규화했다.
	- 이름 별명 목록 대신 Armature 타입을 찾아 이름을 맞췄다.
	- Armature가 없거나 복수인 파일은 경고 후 건너뛰었다.
	- 기준 이름은 정상 모델에 맞춰 Armature로 두고 실행 전 확인창을 제공했다.
	- 도구 진입점은 Tools/FBX Root Normalizer로 정리했다.

- **근거**

	- Unity 임포트 마커를 관리하는 3.4의 기각안과 달리 외부 파일 변환으로 범위를 한정했다. 파일 목록·개수 확인으로 대상을 명시하고, 별명 추가와 폴더 스캔의 관리 부담을 피했다.

- **검증과 한계**

	- 구현 당시 Blender 실제 실행 검증은 대기였다. 미리보기는 두지 않았고 원본 덮어쓰기 복구는 Git을 전제했다. 근본 export 원인이 해결된 것으로 기록하지 않는다.

### 3.10 입력 액션 저장 누락과 생성 클래스 기반 조회

<a id="310-playerinputreader-nre-해결--입력-액션-조회를-generate-c-class로-전환"></a>

> 일자: 2026-08-30

- **문제**

	- 에디터 재시작마다 AimPoint 조회 NRE가 재발했다. Build Scene 실행 뒤에는 메모리에 액션이 추가돼 해당 세션에서만 정상화됐고, 재시작하면 저장되지 않은 원본을 다시 읽어 재발했다.

- **결정**

	- Input Actions 에디터에서 AimPoint·DropWeapon을 추가하고 저장했다.
	- 잘못된 저장 경로의 PlayerInputActionsSetup과 BuildScene의 EnsureActions 호출을 제거했다.
	- Generate C# Class를 켜고 문자열 FindAction 대신 GameInputActions의 프로퍼티를 사용했다.
	- 생성 인스턴스는 Awake에서 준비하고 OnDestroy에서 Dispose하도록 했다.

- **근거**

	- ScriptedImporter가 소스 JSON을 읽는 inputactions 에셋은 메모리 객체에 SetDirty·SaveAssets를 호출해도 원본이 저장되지 않았다. 메모리에서 액션을 찾을 수 있다는 사실과 원본 파일 저장을 구분해야 했다.
	- 코드 저장 대안으로 InputActionAsset.ToJson → File.WriteAllText → 강제 재임포트를 검토했으나 직접 편집으로 처리해 채택하지 않았다. 검토 당시 전용 ToJson과 범용 JsonUtility.ToJson의 포맷 차이, Play 모드 변경 유실을 피하기 위한 Edit 모드 저장을 주의점으로 남겼다.
	- 타입 기반 조회로 이름 오타·누락을 컴파일 시점에 확인하고 입력 전용 폴더로 책임을 모았다.

- **검증과 한계**

	- 조사 당시 원본은 2026-07-27 커밋 이후 변경되지 않았고 AimPoint·DropWeapon도 없었다. 직접 편집 뒤 git status로 원본 파일 변경을 확인했다. 에디터 자동화는 메모리 객체뿐 아니라 디스크의 소스 변경도 확인해야 한다.
	- 생성 클래스 기반 조회 코드를 반영했으며 당시 에디터 재임포트와 클래스 생성 확인은 남아 있었다. 모든 입력 런타임 오류가 사라졌다는 의미는 아니다.

### 3.11 상호작용 버튼 기반 무기 장착·교체·드롭

<a id="311-무기-획득-방식-자동-픽업-폐기-상호작용-버튼으로-통합"></a>

> 일자: 2026-08-30

- **문제**

	- 자동 픽업이 수동 장착 의도와 달랐으며 공격 도중 무기를 밟으면 의도치 않게 교체될 수 있었다.

- **결정**

	| 손 무기 | 바닥 후보 | 상호작용 |
	|---|---|---|
	| 있음 | 있음 | 교체 |
	| 없음 | 있음 | 장착 |
	| 있음 | 없음 | 드롭 |
	| 없음 | 없음 | 무시 |

	- 기존 Q 액션을 재사용하고 Pickup은 범위 진입·이탈만 통지하도록 했다.

- **근거**

	- 기존 Equip·Drop 경로로 처리할 수 있어 새 입력 액션이나 중복 장착 분기가 필요하지 않았다. 방금 버린 무기 재획득 지연도 유지했다.

- **검증과 한계**

	- 구현을 완료했으나 당시 Play 검증은 대기였다. 현재 입력·획득 후보 책임은 3.31에서 PlayerCombatInput으로 분리했다.

### 3.12 근접 판정 시점과 공격 모션 속도 동기화

<a id="312-근접-히트-판정-animation-event-이관--공격속도-재생속도-동기화-구현-완료"></a>

<a id="37-근접-히트-판정-타이밍-animation-event-채택"></a>

> 일자: 판정 방식 결정 2026-08-22, 판정 범위 추가 결정·구현 2026-08-30

- **문제**

	- Animation Event 판정을 실제 코드로 옮기고 공격속도 증강 때문에 모션 길이가 쿨다운을 넘는 상황을 처리해야 했다.

- **결정**

	| 주제 | 결정 |
	|---|---|
	| 근접 판정 | 이벤트가 ResolveAttack 호출 |
	| 판정 위치·방향 | 스윙 시작이 아니라 실제 판정 시점에 읽음 |
	| 무기 교체 | 진행 중 공격 모션을 취소 |
	| 모션 속도 | 상태별 speedParameter 사용 |
	| 근접 전용 대기 상태 | MeleeWeapon이 소유 |
	| 컨디션 배율 | 중복 캐시·enum 리플렉션 제거 |
	- 판정 시점은 코드 지연 타이머 대신 Animation Event로 정했다(2026-08-22). 판정 방식은 OverlapSphereNonAlloc 순간 판정부터 적용하고 넓은 스윙에는 여러 이벤트를 허용했다(2026-08-30).

- **근거**

	- 공격 중 이동·회전이 가능해 시작 시점 캐시는 시각·판정 괴리를 만든다.
	- Animator.speed는 다리까지 가속하므로 공격 상태의 속도만 조절했다.
	- 원거리에 의미 없는 pending 플래그를 공통 기반에 두지 않았다.
	- 상한은 실제 가독성 문제나 추가 속도 채널이 생기기 전에 도입하지 않았다.
	- 순간 판정은 실제 타격을 확인하기까지의 구현량을 줄이기 위한 선택이었다. 손·무기 Trigger 구간에는 형상 저작·중복 명중 관리·판정 반경 재정의가 필요해 처음에는 보류했다.

- **검증과 한계**

	- 당시 코드 작성은 완료했으나 Controller 설정·클립 이벤트·필드 연결과 Play 확인은 남아 있었다. 이 상태를 실제 동작 통과로 해석하지 않는다. 후속 생명주기는 3.14, 공통 실행·모션은 3.31에서 변경했다.
	- 초기 두 판정 방식의 성능 차이는 실측하지 않았다. 빠른 대상 누락이나 시각·판정 괴리가 관찰되면 전환한다는 조건을 두었고 실제 손·무기 Collider 전환은 3.14~3.16에 기록했다.

### 3.14 근접 공격의 타격·종료 관리와 무기 장착 기준

<a id="314-근접-타격-생명주기와-무기-그립-포인트-후속-구현"></a>

<a id="38-펀치-사거리-ik-스트레치-기각-hitradiuslunge-조합으로-방향-확정"></a>

> 일자: 펀치 거리 검토 2026-08-22, 타격 생명주기·장착점 적용 2026-09-21

- **문제**

	- 반복 입력으로 근접 모션이 다시 시작되지 않도록 공격 종료를 관리하고, 짧은 손의 판정과 무기 장착 기준을 정해야 했다.
	- 초기 펀치에서 판정 반경만 키우면 시각적 접촉과 피해 범위가 어긋날 수 있었다(2026-08-22).

- **결정**

	- MeleeWeapon은 Idle에서만 시작하고 타격 구간 뒤에는 모션 종료까지 회복 상태를 유지했다.
	- 손 Trigger Collider를 이벤트로 켜고 끄며 한 공격에서 같은 피해 소유자는 한 번만 맞도록 했다.
	- 좌우 주먹을 교대 사용하고 별도 lunge는 넣지 않았다.
	- 무기 루트의 직접 자식 GripPoint를 WeaponSocket에 정렬했다.
	- 사용자는 IK 팔 늘리기를 제외했다. 새 펀치 클립·hitRadius·짧은 전진을 검토했으나 실제 적용에서는 손 Trigger Collider를 채택하고 별도 전진을 넣지 않았다.

- **근거**

	- 모션 생명주기와 실제 접촉 구간을 구분했다. 장착 기준을 모델 원점과 분리하면 무기별 손잡이 위치를 저작할 수 있었다.
	- 초기 전진 검토는 반경만 확대하는 것보다 실제 거리를 좁혀 시각·판정 괴리를 줄이려는 판단이었다.

- **검증과 한계**

	- 사용자가 Play 동작을 확인했다. GripPoint 없는 기존 무기는 원점 정렬 폴백과 개발용 경고를 유지했다. 후속 공통 공격·이벤트 수신은 3.31로 이관했다.
	- 초기 반경·전진 거리는 미확정이었고 구현 완료로 기록하지 않는다. 사용자가 확인한 범위는 후속 손 Collider·공격 종료·장착점 적용이다.

### 3.18 공격 대상의 피해 소유자 식별

<a id="318-근접-피해-소유자-탐색과-적-접촉-대상-제한"></a>

<a id="324-전투-판정-진단-로그-제거"></a>

<a id="325-피해-소유자-탐색-유틸리티-제거"></a>

> 일자: 피해 소유자 탐색 2026-09-26, 진단 로그·탐색 유틸리티 제거 2026-10-14

- **문제**

	- 풀링된 적의 Transform.root가 개체가 아닌 스포너를 가리켜 피해 대상을 찾지 못했고, 접촉 피해에는 대상 제한이 없었다.

- **결정**

	- Collider에서 부모 방향으로 가장 가까운 IDamageable을 찾아 개체를 식별했다.
	- 공격자 자신을 제외하고 같은 피해 소유자는 공격당 한 번만 처리했다.
	- 당시 접촉 피해는 Player 태그로 제한했다.
	- 인스턴스 ID를 포함한 진단 로그는 조사 후 제거했다.
	- DamageableLookup은 부모 컴포넌트 탐색을 중계하기만 해 GetComponentInParent<IDamageable>(true)를 호출부에서 직접 사용하도록 단순화했다(2026-10-14). 소유자 기준 자기 제외·중복 방지는 유지했다.

- **근거**

	- 관리 계층의 최상위 Transform과 실제 피해 소유자는 다르다. 별도 Hurtbox·캐시보다 짧은 부모 탐색이 현재 규모에 단순했다. 진단 종료 후 체력 비교·계층 문자열 생성도 제거했다.
	- 탐색 유틸리티에 독자적인 책임이 없어 기본 API만으로 같은 계약을 표현할 수 있었다.

- **검증과 한계**

	- 컴파일과 임시 계층의 소유자 선택, Player만 피해 8을 받는 호출 검사를 확인했다. 로그 제거 뒤 실제 전투 회귀는 미실행이었다. 태그는 3.19의 레이어로, 접촉 피해 정책은 [5.29](05-EnemyAnimation.md#529-유형별-공격-피해-정책으로-전환)로 변경했다.
	- 2026-10-14의 유틸리티 제거는 삭제 타입의 참조 부재와 컴파일까지 확인했고 실제 전투 회귀는 미실행이었다. 공통 대상 규칙은 이후 3.31의 AttackTargetRules로 모았다.

### 3.20 배치한 무기를 기준으로 장착점 역산

<a id="320-원거리-무기-자세-미리보기와-grippoint-역산-저작"></a>

> 일자: 2026-09-27

- **문제**

	- 손잡이 기준점을 숫자로 조절하기보다 사격 자세에 무기를 먼저 놓고 장착 기준을 계산할 필요가 있었다.

- **결정**

	- Play 없이 클립을 샘플링하고 현재 무기·소켓 배치에서 GripPoint를 역산했다.
	- 루트 Scale 1을 요구하고 크기는 Model에서 조절했다.
	- 계산과 프리팹 저장을 분리해 GripPoint 위치·회전만 원본에 적용했다.
	- 자세 복원에서 무기 프리뷰를 제외했다.

- **근거**

	- 사용자가 배치한 결과를 기준으로 장착점을 계산하고, 다른 프리뷰 Override나 무기 수정을 함께 덮어쓰지 않도록 했다.

- **검증과 한계**

	- 컴파일·자세 복원·무기 수정 유지·GripPoint 역산·선택 필드 저장을 임시 대상에서 확인했다. 위치 오차는 약 10^-7~10^-6 수준이고 회전 오차는 0도였다. 실제 K2 저작 결과는 사용자 확인 대기였다. 애니메이션 도구 책임은 3.21로 분리했다.

	- Cinemachine 3.1.7 적용 후 컴파일, 직접 API 43개·Play 11개 항목을 확인했다. 건물 접근·Near Clip 안전·FOV·일시정지·복귀·재시작·조준 연결을 포함한다. 모든 모서리·돌출 메시·화면 비율·대상 빌드 성능까지 확인한 것은 아니다. 가림 정책은 3.27, 주시는 3.29로 변경했다.

### 3.29 카메라 근접 정도에 따른 주시 높이 조절

<a id="329-카메라-근접-정도에-따른-주시-높이-선형-보간"></a>

<a id="330-주시-높이-보간의-사용자-수용"></a>

<a id="328-접근복귀-중-상체-기준점의-화면-중앙-유지"></a>

> 일자: 고정 상체 주시·근접 보간 적용·사용자 수용 2026-10-17

- **문제**

	- 평상시에는 발밑을, 장애물로 최대 근접했을 때는 상체를 바라보는 연속 변화가 필요했다.
	- 초기 발밑 주시와 상체 이동 기준이 달라 건물 접근·복귀 때 캐릭터가 화면 중앙에서 벗어났다(2026-10-17).

- **결정**

	- Hard Look At을 CameraProximityLookAt으로 교체했다.
	- Follow·LookAt·Deoccluder의 Camera Target 높이 1.5m는 고정했다.
	- 보정 전 거리를 근접 0%, 보정 후 거리 1m 이하를 100%로 삼아 주시 높이를 0~1.5m 선형 보간했다.
	- Aim 단계에서 주시만 변경하고 FOV 줌은 근접 정도에 포함하지 않았다.
	- 먼저 CinemachineHardLookAt을 추가하고 Follow·LookAt을 높이 1.5m Camera Target으로 통일했다. 이후 평상시 발밑·근접 시 상체를 바라보도록 근접 보간으로 바꿨다(2026-10-17).

- **근거**

	- 추적 기준점 자체를 움직이면 위치 계산에 다시 영향을 주므로 주시 계산을 분리했다. 추가 물리 검사·이전 프레임 상태 없이 보정 전후 거리로 계산했다.
	- 초기 고정 주시는 장애물 보정 뒤에도 같은 Transform을 바라보게 하기 위한 방식이었다. 근접 보간은 이 고정 주시를 대체한 후속 결정이다.

- **검증과 한계**

	- 코드와 Body→Aim 순서를 검토하고 씬 연결을 반영했다. 최초 기록에서는 Play·자동 검증을 하지 않았고 이후 사용자가 높이 변화를 직접 확인해 수용했다. 1m는 조절 가능한 보간 종료 기준이다. 이전 고정 상체 주시의 검사 결과를 근접 보간 구현의 검증으로 재사용하지 않는다.
	- 고정 상체 주시에서는 컴파일·Play 43개·재시작 4개로 NW03·SE04의 FOV별 왕복, 중앙 유지·안전·복원을 확인했다. 최초 NW03 경로는 옆 건물 내부로 들어가 무효였고 통행 가능한 경로로 재검사했다.

### 3.31 플레이어·적의 무기 실행과 사람형 모션 공유

<a id="331-범용-무기와-사람형-모션-통합"></a>

<a id="33-게임플레이--애니메이션-연결부"></a>

> 일자: 초기 책임 분리 2026-08-20, 공통 실행·모션 통합 2026-10-19

- **문제**

	- 플레이어·적의 같은 장착·공격·타격·사람형 모션 규칙을 한 실행 경로에서 관리해야 했다.

- **결정**

	| 구성 | 책임 |
	|---|---|
	| WeaponController | 장착·교체·드롭·내구도·공격 배율·손 선택·공격 진행 |
	| PlayerCombatInput | 입력·조준·획득 후보·도감 기록 |
	| CharacterAnimationController | Animator·클립·속도·하체 혼합·타격·종료 신호 |
	| WeaponBase·MeleeWeapon·RangedWeapon | 쿨다운·근접 명중·발사 |
	| AttackTargetRules | 허용 레이어·가장 가까운 소유자·자기·사망 대상 제외 |

	- 입력/AI → 공통 실행 → 무기·모션 방향으로 연결했다.
	- 모션은 입력·AI·무기를 역참조하지 않는다.
	- Base → 전신 Action → Lower Body 구성으로 이동 속도에 따라 하체만 혼합했다.
	- 공격자·대상·공격 레이어를 무기에 전달하고 투사체는 발사 시 복사·반환 시 정리했다.
	- WeaponPickup.TryClaim으로 소유·지연·중복 획득을 확인했다.
	- 초기 PlayerAnimationController는 AttackPerformed(WeaponCategory)와 정규화 이동 속도를 관찰해 Animator를 갱신했고 WeaponSocket은 Humanoid 오른손 본에 자동 부착했다(2026-08-20). 이후 명시적 모션 재생과 타격·종료 신호 연결로 일부 변경했다(2026-10-19).

- **근거**

	- 같은 규칙의 수정 위치를 통일하면서 입력·AI 판단·플레이어 기록을 분리했다. 기존 순수 관찰자 방식 일부를 명시적 모션 재생으로 바꿔 타격과 종료 신호를 한 경로에서 대조했다.
	- 초기 구조도 표현 코드에 입력·피해 규칙을 넣지 않기 위한 분리였다. 공통화에서는 책임 경계를 유지하며 실행 신호의 전달 방식을 변경했다.

- **검증과 한계**

	- GUID를 보존해 이름·위치를 이관했고 컴파일·플레이어/적 Missing Script 0·저장 후 씬 연결을 확인했다.
	- 초기에는 직접 플레이를 하지 않았고 첫 재공격 오류를 3.32에서 수정했다.
	- 기본 적 적용은 [5.33](05-EnemyAnimation.md#533-공통-무기모션과-기본-적-펀치), 무기 탐색·획득 AI는 미구현이다.
	- 2026-08-20의 관찰자 구조는 설계 확정·구현 착수 당시 기록이며 현재 계약을 뜻하지 않는다. 당시 별도 실행 검증 기록은 없다.

### 3.32 공격 상태 경로 불일치로 인한 재공격 차단 수정

<a id="332-공격-상태-경로-이관-누락-수정"></a>

> 일자: 2026-10-19, 사용자 확인 2026-10-19

- **문제**

	- 첫 근접 공격 뒤 재공격이 막혔다. 레이어는 Action으로 바뀌었지만 내부 상태 머신은 Upper Body로 남았다.

- **결정**

	- Controller와 설정 도구가 레이어·상태 머신 이름을 함께 Action으로 저장하도록 고쳤다. 기존 공격 간격·타격 구간·종료 방어는 유지했다.

- **근거**

	- 공통 모션이 기대한 Action 경로 해시가 없어서 진입·타격·종료 신호를 거절하고 무기 상태를 Idle로 돌리지 못하는 경로였다.

- **검증과 한계**

	- 수정 전 HasState는 Action=false·Upper Body=true였다. 수정 후 근접·좌우 펀치 Action 경로 true와 구 경로 false, 컴파일 무오류를 확인했다. 조사 당시 편집 상태였으므로 첫 공격 뒤 상태를 실시간 관측한 것은 아니다. 이후 사용자가 재공격 정상 동작을 확인했다. 사격 크래시의 원인 해결과는 구분하며 관련 한계는 [5.33](05-EnemyAnimation.md#533-공통-무기모션과-기본-적-펀치)에 남겼다.
