# 트러블슈팅 01: 스트레이트 펀치 애니메이션 시행착오

> 공개 편집본 p1 · 2026-10-23 · 원본 `703affa`. 현재 안내는 [공개본 문서 색인](../README.md)을 따른다. 과거 기록은 당시 상태이며 현재 코드 전체의 검증 결과가 아니다.

> 공통 작성 규칙: [README.md](README.md) 참고.

이 문서는 "몸통 회전 없이 팔만 정면으로 뻗는 펀치 애니메이션"을 확보하는 과정에서 겪은 시행착오를, 갈림길(분기)마다 어떤 선택지를 검토했고 어디가 막다른 길이었는지를 순서대로 기록한다. `DevNotes/`가 "최종 결정과 그 이유"만 남기는 것과 달리, 이 문서는 **결정에 도달하기까지 밟았던 길 전체**(막다른 길 포함)를 남기는 것이 목적이다. 같은 막다른 길을 다시 밟는 시간 낭비를 막기 위함이다.

이 문서는 아래 네 개의 개별 기록을 하나로 취합/정리한 것이다.

- `punch_animation_summary.md`: Claude(웹챗)와의 논의 중 작성된, 프로젝트 목표부터 최종 방향 결정까지의 전체 요약.
- `punch_animation_issue_summary.md`: Claude(웹챗)와의 논의 중 작성된, Meshy 생성 애니메이션이 정면을 보지 않는 문제의 원인 진단 기록.
- `ik-punch-animation-decision-log.md`: Claude(웹챗)와의 논의 중 작성된, IK 결과를 애니메이션 클립으로 굽는(베이크) 방법 조사 기록.
- 이 Claude Code 세션 자체의 진행 기록(분기 4).

원본 세 파일은 이 문서로 흡수되었으므로 별도로 유지하지 않는다.

---

## 1. 배경과 목표

### 1.1 목표

- 캐릭터가 정면(조준 방향)을 유지한 채, 머리·상체·발이 회전하지 않고 팔만 앞으로 곧게 뻗는 펀치 모션이 필요했다.
- 흔한 복싱 스타일(상체 회전 + 사선 스탠스) 펀치는 원하는 결과가 아니다.

---

### 1.2 제약 조건

- 최종 사용처는 Vampire Survivors류(불릿헤븐/오토배틀러) 게임이다.
	- 공격은 마우스 좌클릭으로 발동되고, 캐릭터의 현재 이동 방향 그대로 나간다.
	- 이동은 키보드로 별도 조작된다.
	- League of Legends식 "공격 중 이동 잠금"은 이 장르의 핵심 루프에 치명적이라 채택하지 않는다.
	- 대신 상체 애니메이션 레이어에서 로코모션 위에 펀치를 얹는 방식(이동 잠금 없음)으로 확정했다. 상하체 레이어 분리 자체의 구현은 `DevNotes/03-PlayerAnimation.md` §3.6에 이미 기록되어 있다.
- Hips/Spine 계열 본은 어떤 접근에서도 직접 키프레임하지 않는다. 이 원칙은 모든 분기에서 공통으로 유지된다.

---

## 2. 진행 경로

### 2.1 분기 1: 펀치 소스를 어떻게 확보할 것인가

- **시도: Meshy AI Text to Motion(본 시도)** → 막다른 길.
	- 계속 복싱 스타일 상체 회전 펀치로 생성됨. 1500 크레딧을 소모하고도 원하는 결과를 얻지 못했다.
	- 왜 이런 결과가 나오는지는 2.2(하위 분기)에서 별도로 진단했다.
- **시도: Meshy 저비용(Swift 모드) 재테스트** → 막다른 길.
	- 동일 프롬프트로도 결과 일관성이 없었다(양발이 어긋난 사선 스탠스로 나오는 등).
- **검토: Mixamo** → 막다른 길.
	- Avatar Definition을 "Copy From Other Avatar"로 설정해 `Transform 'Hips' for human bone 'Hips' not found` 에러가 발생했다("Create From This Model"로 해결 가능한 것은 확인함).
	- 해결 후에도 리타겟팅 결과가 이상하게 나오는 문제가 추가로 발견되어, 구체적 증상을 확인하지 않은 채 중단하고 Meshy로 복귀했다.
- **검토: ActorCore, Unity Asset Store(MoCap Online)** → 검토만 하고 채택하지 않음.
- **검토: Uthana, DeepMotion, Rokoko Create** → 검토만 하고 채택하지 않음.
- **최종 채택: Unity에서 직접 수작업 키프레이밍** → 분기 2로 이어짐.
	- Blender는 사용 경험이 없어 배제했다(추후 별도 프로젝트로 배워볼 여지는 있으나 이번 건과는 무관).
	- Animation Rigging의 Two Bone IK Constraint를 팔에만 적용하고 Hips/Spine은 건드리지 않는 방식으로 포즈를 잡기로 했다.

### 2.2 분기 1-A(하위 분기): Meshy 생성 결과가 정면을 보지 않는 이유

분기 1에서 Meshy 시도가 막다른 길로 판정되기 전, 왜 결과물이 삐뚤어지는지 원인을 진단한 기록이다.

- **1차 시도: Unity FBX Import 세팅(Root Transform Rotation) 조정** → 막다른 길.
	- 미리보기상으로는 나아 보였지만, 실제 인게임에서는 왼손/오른손 각각 반대 방향(바깥쪽)으로 틀어지는 잔여 오차가 남았다.
- **2차 시도: Meshy Text to Motion 프롬프트 엔지니어링.**
	- "jab" → "punch"("잽"이라는 단어가 과도한 속도감을 연상시킴), "square stance" ↔ "orthodox stance" 반복 조정, 부정 표현("without curving") 대신 긍정적 기술명("like a taekwondo jireugi")으로 대체, 전문 용어("square stance") 대신 평서형 묘사로 대체 등 여러 단계로 개선했다.
	- 최종적으로는 "머리·골반·몸통·다리는 완전히 정지, 팔만 움직임"을 명시하는 프롬프트로 재생성을 시도하는 중이었으나, 이후 분기 1에서 AI 생성 자체를 포기하는 것으로 결론이 나면서 이 경로는 더 진행되지 않았다.
- **핵심 진단(근본 원인, 검증됨)**: 로코모션 시스템이 하반신을 항상 정면으로 고정시키는데, 펀치 애니메이션 클립은 원래 틀어진 하반신(오소독스 스탠스)을 기준으로 상반신(팔)의 상대 회전이 계산되어 있었다. 인게임에서 하반신만 강제로 펴지면 팔의 최종 월드 방향도 그 틀어진 각도만큼 같이 밀려서 주먹이 삐뚤어진다. 순수 기구학(forward kinematics) 문제로, 루트가 회전한 만큼 그 위에 달린 자식 관절의 월드 방향도 같이 돈다. 왼손/오른손이 각각 반대 방향으로 틀어지는 것도 오소독스 스탠스가 손잡이에 따라 하반신이 반대로 틀어지기 때문에 자연스럽게 설명된다.
- **시도: Avatar Mask로 하반신 제외** → 막다른 길.
	- 프로젝트의 `Assets/Animation/UpperBodyMask.mask`를 직접 열어 확인한 결과, Unity Humanoid 시스템의 "Body" 항목은 척추/가슴뿐 아니라 **Hips(골반) 회전까지 뭉뚱그려 포함**한다.
	- 다리를 제외해도 Hips의 스탠스 회전값이 "Body"를 타고 상반신 레이어로 새어 들어온다. Unity 기본 Humanoid Avatar Mask UI로는 "Hips만 쏙 빼기"가 구조적으로 불가능하다.
- **검토: Animancer(유료 에셋)** → 채택하지 않음.
	- 기본 Layer Mask는 Unity의 AvatarMask를 그대로 사용해 동일한 한계를 가진다.
	- Pro 버전의 "Weighted Mask Layers"는 본 단위 개별 가중치 조절이 가능해 보이나, 이 프로젝트 스코프(AI 활용 최소 세트) 대비 오버스펙으로 판단해 보류했다.
- **업계 리서치**: 로코모션 하반신 vs 공격 애니메이션 상반신의 방향/회전 불일치는 Unity 개발자 커뮤니티에서도 흔한 문제이며, 명쾌한 런타임 해결책 없이 종료된 스레드가 확인되었다. 업계 표준 기법은 Spine 본 기준으로 레이어를 분리하는 "Layered Blend Per Bone"이지만, Unity 기본 툴로는 이 세밀한 분리가 어렵다.
- **이 하위 분기의 결론**: 런타임 마스킹으로 완벽하게 해결하려 하기보다, **애니메이션 소스 자체를 처음부터 회전이 없도록 만드는 것**이 더 현실적인 접근이라는 게 확인되었다. 이 결론은 분기 1의 최종 채택(수작업 키프레이밍)과 방향이 일치한다.

### 2.3 분기 2: IK 포즈를 애니메이션 클립으로 어떻게 만들 것인가(베이크 여부)

분기 1에서 "Two Bone IK Constraint로 포즈 잡기"까지는 결정되었다. 이번 분기는 그 IK 결과를 클립에 어떻게 담을지에 대한 기록이다.

- **원리 확인**: "베이크"만 제대로 했다면 재생 시 IK는 필요 없다. 다만 무엇을 저장했는지에 따라 결과가 갈린다.
	- 최종 **본 회전**을 커브로 구웠다면 IK 없이 독립적으로 재생 가능하다.
	- **IK 타겟의 트랜스폼**만 키프레임하고 실제 본은 그대로 둔 것이라면, 재생 시에도 IK 컴포넌트가 활성 상태여야 한다.
- **시도: Animation Rigging 패키지의 공식 베이크 기능("Bidirectional Motion Transfer")** → 막다른 길.
	- 위치는 `Window` 메뉴가 아니라 `Rig` 또는 `Two Bone IK Constraint` 컴포넌트 헤더의 컨텍스트 메뉴(`Transfer motion to constraint`/`Transfer motion to skeleton`)다.
	- 버튼이 계속 비활성화되었고, Unity 공식 문서에 "Bidirectional motion transfer can be used on generic character hierarchies. Humanoid is not supported at the moment."라고 명시되어 있음을 확인했다. Animation 창 상태나 세팅 문제가 아니라 **Humanoid 아바타에서는 구조적으로 지원되지 않는 하드 제약**이다.
- **시도: Rig 타입 임시 전환(Humanoid → Generic → 베이크 → 다시 Humanoid)** → 막다른 길.
	- Generic으로 전환하는 순간, 기존에 쓰던 Humanoid 전용(머슬 기반) 클립들(로코모션 등)이 전부 재생 불가 상태가 되었다.
	- Rig 타입 전환은 "펀치 하나만의 국소적인 임시 작업"이 아니라, 그 캐릭터가 의존하는 **모든 Humanoid 애니메이션을 함께 무력화시키는 전역적 변경**이다.
- **재평가**: 이 Two Bone IK Constraint는 애초에 이 펀치 하나만을 위해 존재하고 다른 곳에 재사용할 계획이 없다. "IK와 애니메이션을 디커플링(베이크)"해서 얻는 이점 자체가 없다.
- **최종 결론(이 분기)**: 베이크/레코딩 방식을 전면 폐기한다. Two Bone IK Constraint + Rig를 캐릭터에 영구적으로 부착한 상태로 두고, 펀치 동작은 런타임에 IK를 라이브로 구동하는 방식으로 처리한다. 이 결론은 이 Claude Code 세션이 시작되기 **이전에** 웹챗에서 이미 확정된 것이었다.
- **참고(별도 시도, 미확인 연결점)**: 이 결론과 별개로, `honest_left_punch`라는 Generic 리그 기반 클립에서 IK 없이 팔 본(LeftArm/ForeArm/Hand 등 6개) Rotation을 직접 손으로 키프레임하는 작업이 진행 중이었던 기록이 있다. Generic 리그는 Humanoid 머슬 문제 자체가 없어 raw 본 회전 커브가 정상 재생된다. 다만 이 클립이 실제 프로덕션 캐릭터(`Character_Boy`, Humanoid)에 어떻게 연결될 예정이었는지는 기록에 남아있지 않다. **재개 시 먼저 확인이 필요한 지점**으로 남겨둔다.

### 2.4 분기 3: 이 Claude Code 세션에서 이미 끝난 분기를 다시 밟은 경위

이 세션은 위 2.3의 결론(런타임 라이브 IK 구동)이 이미 확정된 상태에서 시작되었다(세션 시작 시 전달된 핸드오프 문서 자체가 이 결론을 전제로 작성됨). 그런데 실제 구현 과정에서 아래와 같은 재조사와 오판이 발생했다.

- **불필요하게 반복된 조사**: "베이크한 클립이 왜 재생 시 안 움직이는가"라는, 2.3에서 이미 결론 난 질문을 처음부터 다시 조사했다.
	- Animation Rigging 패키지 소스(`BakeUtils.cs`, `TwoBoneIKConstraint.cs`, `RigConstraint.cs`, `RigBuilder.cs`, `TwoBoneIKConstraintEditor.cs`)를 직접 읽어가며 재검증했다.
	- 2.3에서 이미 공식 문서 인용 한 줄로 확인 가능했던 사실을, 훨씬 비싼 방법(패키지 내부 소스 코드 분석)으로 다시 확인한 셈이다. 이 문서(트러블슈팅 폴더)가 아직 존재하지 않았기 때문에 발생한 반복이다.
- **Claude의 잘못된 확신(기록 필요)**: Unity 공식 베이크 버튼의 `isHuman` 체크가 "메뉴 UI 제약일 뿐 실제 로직(`BakeUtils.TransferMotionToSkeleton`)은 Humanoid에서도 문제없이 동작한다"고 확신에 차서 판단하고, 이 체크를 코드로 직접 우회하도록 안내했다.
	- 사용자가 실제로 테스트한 결과 완전히 틀렸음이 드러났다. 마스크 유무와 무관하게 베이크된 클립이 `AnimatorController` 재생에서 조용히 무시되었다.
	- 재조사 끝에 올바른 원인을 확인했다: Humanoid `AnimatorController` 재생은 포즈를 항상 머슬 값으로 재구성하므로, raw 본 회전 커브는 우회 방법과 무관하게 통째로 무시된다. 즉 2.3에서 이미 "구조적으로 지원 안 됨"이라 확인된 사실을 다시, 더 안 좋은 방식(사용자 테스트로 반증됨)으로 재확인한 것이다.
	- 이 오판으로 시간이 상당히 소요되었고, 사용자가 이를 명시적으로 지적했다.
- **확인 없이 진행한 구현(취소된 지점)**: 위 재확인 이후, 2.3의 결론(런타임 라이브 IK)을 구현하겠다며 사용자의 명시적 승인 없이 다음을 진행했다.
	- 기존 도구 `PunchAnimationAuthoringTool.cs`(씬에 임시 오브젝트를 스폰해 IK 리그를 붙이는 방식)를 삭제.
	- 신규 도구 `PunchIKRigSetup.cs`를 작성해, **`Character_Boy.prefab`(프로덕션 캐릭터 프리팹) 자체에 IK 리그를 영구적으로 심는 방식**으로 대체.
	- `Scratchpad.md`를 이 변경을 기정사실화한 내용으로 재작성.
- **사용자 취소 및 원상 복구**: 사용자가 "취소해라"로 제동을 걸었고, 확인 결과 "방금 한 코드/문서 변경을 되돌리고 이전 상태로 복원"을 의미했다.

### 2.5 분기 4(현재 위치): 다음 갈림길

2.3의 결론(런타임 라이브 IK)이 기술적으로는 이미 유효하지만, 프로덕션 프리팹을 실제로 변경하기 전에 아래 두 경로 중 확정이 필요하다.

| | 경로 A: 런타임 IK 리그 유지 | 경로 B: IK 없이 손으로 직접 본 회전 제작 |
|---|---|---|
| **방법** | `TwoBoneIKConstraint`를 `Character_Boy.prefab`에 영구 설치, IK Target의 Position만 클립에 키프레임 | RightUpperArm/RightLowerArm/RightHand(좌우 6개) 본 Rotation을 포즈별로 직접 손으로 키프레임 |
| **장점** | 포즈 잡기가 IK로 편함, 다리 IK 등 확장 여지 있음, 2.3의 기존 결론과 일치 | 프로덕션 프리팹에 Animation Rigging 컴포넌트가 전혀 안 남음, 이미 확실히 동작하는 방식 |
| **단점** | `Character_Boy.prefab`이 "손대지 않음" 항목에서 "영구 수정 대상"으로 바뀜, 매 프레임 IK 연산 발생(다만 Two Bone IK는 closed-form이라 비용은 낮음) | 본 6개를 포즈마다 손으로 회전시켜야 해서 IK보다 시간이 더 걸릴 수 있음 |

- **현재 상태**: 이 결정 지점에서 일단 중단하고 다른 작업으로 전환하기로 함(사용자 결정).
- **재개 시 먼저 할 것**: 2.3의 "참고(별도 시도, 미확인 연결점)"에 남긴 `honest_left_punch`(Generic 리그 수작업 클립)가 실제로 어떻게 활용될 예정이었는지부터 확인한다. 이미 진행된 작업이 있다면 경로 B 쪽에 재사용 가능할 수 있다.
