## 1. 표기

- em dash(—)를 쓰지 않는다. 부연 설명이 필요하면 문장을 나누거나 괄호를 쓴다.
- 하위 불릿 들여쓰기는 탭을 쓴다. 스페이스 2칸은 시각적 구분이 약해 사용자 요청으로 탭으로 전환(2026-08-05). 탭은 렌더러/에디터마다 처리 폭이 달라 중첩 리스트가 깨질 위험이 있다는 점은 감수한다.
- 인용부호는 용도에 맞게 구분한다.
	- 실제 대화나 직접 인용에는 큰따옴표(" ")를 쓴다.
	- 강조하거나 비유적으로 표현할 때는 작은따옴표(' ')를 쓴다.
	- 책 제목·프로젝트명 등 고유명사를 가리킬 때는 큰따옴표를 써도 된다.

---

## 2. 중복 방지

- 하나의 사실/결정은 그 시스템의 홈 챕터 한 곳에만 자세히 쓴다. 다른 장에서 같은 내용이 다시 필요하면 전체를 재서술하지 않고 'N장 참고' 식으로 짧게 교차 참조한다.
- 예외: 10장(MVP 범위 요약)이나 변경 이력 표처럼 '한눈에 요약/기록'하는 것 자체가 목적인 챕터의 반복은 의도된 것이므로 대상이 아니다.

---

## 3. 결정 사유 보존

<a id="3-사유왜-이렇게-정했는지-서술"></a>

- 결정 사유는 삭제하지 않는다. 사유가 없으면 나중에 같은 논쟁이 반복되거나, 이미 기각된 안이 다시 제안될 수 있다.
- 다만 여러 문장/불릿으로 장황하게 늘어놓지 않고 한 단락으로 압축한다.
- 예외: 사용자가 애초에 설계한 적 없는 것으로 확인된 개념처럼, 살릴 가치가 없는 경우엔 사유 서술 없이 그냥 삭제해도 된다.

## 4. 현행 기준과 과거 기록 분리

<a id="4-히스토리-vs-스펙-분리"></a>

- 기준 문서 본문은 현재 규칙을 중심으로 쓴다. 주요 변경은 하단 변경 이력에서 요약하고, 장기적으로 필요한 판단 경위·사유는 개발 노트나 회의록 등 성격에 맞는 보존 기록에 남긴다.
- 구현 세부 결정의 히스토리는 `DevNotes/`의 관련 기록 파일로 이관한다(`CLAUDE.md`에 이미 명시된 원칙).
- 확정된 스펙은 긍정문으로 서술한다.
	- 판별 기준: 부정문의 대상이 한때 검토되다 폐기된 '이름 붙은 개념/시스템'(예: 서브타입 분류, 무기-적 상성)이면, 그 이름을 언급하지 않고 현재 동작만 긍정문으로 쓴다.
	- 반대로 부정문의 대상이 현재 스펙 자체가 지키는 불변 조건/보장(예: '완전 무력화 상태는 만들지 않는다')이면, 폐기된 대안을 가리키는 게 아니므로 부정문 그대로 둬도 된다.

## 5. 문서 정보·변경 이력

<a id="5-편집-절차"></a>

- **상단 문서 정보**
	- 버전·작성일·수정일·역할·상태 등 기존 정보는 `항목 | 내용`의 2열 표로 정리한다.
	- 문서에 필요한 항목만 사용하며, 없는 날짜나 상태를 형식을 맞추기 위해 추가하지 않는다.
- **변경 이력**
	- 변경 이력이 있는 문서는 최근 주요 변경을 최대 5건만 남기고, 건당 한 문장으로 요약한다.
	- 규칙·범위·결정·문서 운영이 바뀌면 기존 버전을 올리고 변경 이력에 추가한다.
	- 오탈자·서식·제목·참조 경로만 정리한 경우 버전과 변경 이력은 유지하고 편집 내역은 Git으로 확인한다.
	- 오래된 행을 덜어내기 전에 중요한 사유·결과가 본문이나 보존 기록에 있는지, 과거 기록이 Git에 보존되어 있는지 확인한다.
	- 버전 번호는 과거 식별자를 유지하며, 남긴 행에 맞춰 다시 매기지 않는다.
	- 변경 이력이 없는 문서에 형식을 맞추기 위한 새 변경 이력을 만들지 않는다.
- **문서별 예외**
	- 개별 회의록은 회의일만 한 줄로 표시하며, 버전·수정일·변경 이력은 두지 않는다.
	- 개발 노트의 결정 기록은 항목별 날짜를 사용하며, 파일 버전·별도 변경 이력은 두지 않는다.
- 비영구 문서인 `HANDOFF.md`와 `DiscussionDraft.md`는 버전·수정일·문서 내부 변경 이력을 두지 않는다.
- 비영구 문서는 제목·`0. 일러두기`·고정 H2 형식을 유지하고, 현재 작업 본문만 교체한다.
- 비영구 문서의 과거 본문은 Git 이력으로 확인한다.
- 다른 문서가 참조하는 '기반 문서' 버전 표기(`DevPlan.md`/`Systems.md` 상단의 `GDD.md` vX.X 등)도 같이 갱신한다.

## 6. 출처와 확정 여부

<a id="6-출처-표시"></a>

- Claude가 제안한 문장인지 사용자 본인 생각인지 항상 구분해서 알린다. 사용자가 동의하기 전에는 문서에 조용히 흡수시키지 않는다.

## 7. 제목·목록 구성

<a id="7-섹션-구성"></a>

- `##`/`###` 제목에는 GDD.md 방식의 번호를 단다. `##`는 문서 내 순서대로 1, 2, 3..., 그 아래 `###`는 소속 `##` 번호를 이어받아 N.1, N.2...로 붙인다(예: `## 2` 아래 세 번째 `###`는 `2.3`).
- `###` 제목과 그 아래 내용을 하나의 **섹션**으로 정의한다.
- 모든 섹션은 위에 구분선(`---`)을 둔다. 같은 장(`##`) 안에 섹션이 여러 개 이어져도(예: 5.1, 5.2, 5.3...) 각 섹션 앞마다 빠짐없이 구분선을 넣는다.
- 예외: `##`(장) 바로 다음에 `###`(섹션)가 곧바로 나오는 경우, 그 사이의 구분선은 생략한다. 장 제목 자체가 이미 구분 역할을 하므로 구분선이 중복된다.
- 제목은 문서의 장·절과 독립적인 주제를 구분할 때 사용한다. 같은 주제 안에서 내용을 분류하는 항목명은 상위 불릿으로 쓰고, 해당 내용은 그 아래에 배치한다.
	- 상위 불릿의 분류 항목명은 굵게 표시해 본문과 구분한다. 예: `- **문제**`.
	- '문제'·'결정'·'근거'·'확인 사항'처럼 역할을 표시하는 항목명 전반에 적용한다.
	- 설명과 요점 목록은 하위 불릿으로 쓰고, 표·코드 블록 등은 상위 불릿에 속하도록 들여쓴다.
	- 내용의 길이·문단 수·표 포함 여부를 기준으로 항목명을 제목으로 바꾸지 않는다.
	- 기존 문서는 수정 대상 범위에 적용하며, 문서 전체의 일괄 변환은 별도 요청 시 진행한다.

예시:

```markdown
- **문제**
	- 증강 정의·플레이어별 레벨·선택 UI·실제 스탯 적용의 책임을 분리해야 했다.
```

## 8. 문체·서식

<a id="8-서식톤"></a>

- 가독성을 위해 불릿, 블록쿼트(`>`), 표 등을 적극 활용한다.
- 불릿을 쓸 때는 가능하면 한 불릿당 하나의 문장으로 구성한다.
- 불릿 간 종속 관계가 명확하면 하위 불릿으로 구성한다.
- 간결성을 우선한다. 장황한 설명보다 짧고 명확한 표현을 쓴다.
- 선언적 형태를 우선한다. 완결된 문장보다 점(bullet) 스타일의 서술을 우선한다.
- 불필요한 서술은 걷어낸다. 문장을 완성하기 위해 덧붙이는 수식어·완충 표현·군더더기는 정보값이 없으면 뺀다.
- 텍스트는 담백한 톤으로 쓴다. 여기서 담백함은 **감정적 뉘앙스를 배제한 객관적·전문적 어조**를 뜻한다.
	- 감정을 나타내는 단어('좌절감을 준다', '재미있다', '부담스럽다' 등)로 반응을 서술하지 않는다. 대신 관찰 가능한 구조/현상으로 서술한다.
	- 예시: '돈 냈는데 이번 런엔 안 나온다는 좌절감을 준다' (X) → '결제 이후에도 실제 획득이 확률에 달려 있어, 결제와 결과가 직접 연결되지 않는다' (O)
	- 강조(볼드체)나 비유적 표현 자체를 금지하는 건 아니다. 다만 어조가 감정을 자극하는 방향이 아니라 사실을 명확히 하는 방향이어야 한다.
- **이미지**
	- 문서용 이미지는 `Docs/Images/`에 보존하고 주제·날짜·내용을 식별할 파일명을 쓴다. 원본은 유지하며 문서에서 상대경로로 참조한다.
	- 설명을 이해하는 데 필요한 이미지만 해당 내용 가까이에 배치하고, 비교가 필요하면 표로 나란히 놓는다.
	- 캡션으로 생성 시안·실제 구현·검증 결과를 구분한다. 미채택 시안이나 이미지 속 배경·소품을 확정 설정으로 해석하지 않는다.

## 9. 적용 범위·문서 독립성

<a id="9-문서-간-독립성"></a>

- 이 가이드는 프로젝트의 구조화된 Markdown 문서에 기본 적용한다.
- 문서 성격상 맞지 않는 규칙은 대상 문서의 `0. 일러두기`에서 적용 범위와 이유를 명시한 경우에만 예외로 둔다.
- `GDD.md` 본문은 `DevPlan.md`/`Systems.md`/`DevNotes/`의 존재나 개발 단계 번호('2단계', '3단계' 등)를 언급하지 않는다.
- 시점/우선순위 표현이 필요하면 단계 번호 대신 상태 표현('MVP 포함', '후순위', '포스트-MVP', '범위 밖')을 쓴다.
- GDD 내부 챕터·섹션 번호('5.5 참고', '11장 참고' 등) 교차 참조는 이 규칙의 대상이 아니다.
